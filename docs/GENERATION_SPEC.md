# AI 酒馆生成规范

版本：`1.0.0-draft`

本规范定义当前 AI 模型在每个剧情回合中需要生成的内容、允许产生的状态变化、角色卡和世界书的同步规则，以及后端在保存结果前必须执行的校验。供应商差异不得改变本规范。

对应的机器可读校验文件为 [`schemas/generation-output.schema.json`](../schemas/generation-output.schema.json)。

本文使用以下规范词：

- **必须**：实现不可省略，否则该回合无效。
- **应该**：默认遵守，只有明确理由时才可偏离。
- **可以**：可选能力。

## 1. 设计目标

每轮生成必须同时处理以下四类信息，但不能混为一谈：

1. **本轮剧情**：本轮已经发生的叙述、对话和动作。
2. **角色当前状态**：位置、身体状况、情绪、正在执行的目标等可变化状态。
3. **角色卡演化**：身份、长期目标、稳定信念、永久伤痕等足以改变角色长期扮演方式的变化。
4. **世界书变化**：统治者、地点、组织、规则和历史事件等对多个角色或未来场景有持续影响的世界事实。

生成器必须让剧情结果与状态变化一致，避免故事写了角色受伤、死亡或改换阵营，但后续提示词仍继续使用旧设定。

## 2. 信息分层

### 2.1 基础角色卡

玩家导入或创建的 Tavern Character Card V2 是角色的基础定义。模型生成的剧情不得直接覆盖基础卡；玩家通过人物管理明确确认的编辑可以更新本地基础卡，并保留独立审计记录。

以下字段默认视为作者控制字段，不允许模型自动改写：

- `system_prompt`
- `post_history_instructions`
- `creator_notes`
- `creator`
- `character_version`
- 未知的第三方 `extensions`

### 2.2 角色演化层

角色演化层记录已经被剧情确立、会长期改变角色扮演的内容。运行时使用“基础角色卡 + 演化层”组成当前有效角色卡。

适合进入演化层的变化包括：

- 新身份、头衔、职业或阵营归属。
- 长期目标被建立、放弃、替换或完成。
- 经历重大事件后形成的稳定信念、恐惧、誓言或立场改变。
- 永久伤痕、残疾、能力获得或能力永久丧失。
- 已经揭露且会长期影响行为的秘密。
- 与角色扮演密切相关、预计跨多个场景持续存在的重要关系变化。

以下内容不得仅因单轮表现就进入演化层：

- 一时的愤怒、喜悦、犹豫或疲惫。
- 当前姿势、位置、服装细节或正在执行的普通动作。
- 尚未被剧情确认的猜测、幻觉、谎言或计划。
- 只影响一轮或一个短场景的临时效果。

角色演化层应保存在命名空间扩展字段 `extensions.ai_tavern.evolution` 中。永久合并回角色卡核心字段前，必须向玩家展示差异并取得确认。

### 2.3 角色当前状态

每个参与剧情的角色必须拥有独立的当前状态。状态至少可以表达：

- 是否在场、当前位置和去向。
- 存活状态、健康、伤势和临时效果。
- 当前情绪、警觉度和对局势的即时态度。
- 当前目标、正在执行的动作和受阻原因。
- 当前持有的重要物品和资源。
- 已知事实、误解、怀疑和未被该角色知晓的信息边界。
- 与其他角色的即时关系倾向。

状态变化只写入发生变化的字段，不得在每轮重写整个角色对象。

`present=false` 表示角色当前不在场。模型不得直接让该角色说话或行动；如果剧情明确使其重新登场，本轮必须包含回归事件，并在 `sceneTransition.presentCharacterIds` 中提交回合结束时的真实阵容。被玩家停用的角色不会进入可用角色 ID，模型不得重新启用或扮演该角色。

### 2.4 世界书层

世界书保存对未来场景有持续影响的世界事实。游戏中产生的变化先写入会话动态世界书，并覆盖或补充基础世界书的检索结果。

适合写入世界书的变化包括：

- 地点被摧毁、占领、封锁、重建或改名。
- 政权、统治者、组织结构或阵营关系发生变化。
- 公开法律、魔法规则、社会规则或自然规则发生变化。
- 重要人物死亡、失踪、继位或成为公开事件。
- 足以影响多个角色与后续场景的重大历史事件。

角色的短期情绪、私人物品和普通关系变化不应写入世界书。

## 3. 单回合处理流程

每个回合必须按以下顺序处理：

1. 读取有效世界书、基础角色卡、角色演化层、各角色当前状态、关系状态、剧情摘要和最近回合。
2. 读取玩家本轮选择、角色言行输入和当前有效的剧情走向输入。
3. 生成本轮叙述、角色动作和角色对话。
4. 判断接下来需要“回应提议”还是“决定行动”，并生成相应候选项。
5. 提交本轮结束时的当前位置和完整在场阵容。
6. 提取本轮造成的其他角色状态、关系、角色卡演化和世界书变化。
7. 评估当前剧情走向是否已经被实际剧情完成。
8. 对输出执行结构、引用、知识边界和冲突校验。
9. 将剧情消息和所有状态变化作为一次原子提交保存。

任一步校验失败时，不得只保存剧情文本而丢弃状态变化，也不得只修改角色卡或世界书而不保存对应剧情。

**防重复推进**：本轮 `turn.scene` 与最近 4 回合（含上一回合）场景逐一进行字符 n-gram 相似度比较，任一达到阈值（默认 0.55）即视为无效输出，通过修复请求要求模型跳过已展示内容并推进剧情；修复后仍重复则该回合失败，不写入任何状态。重生成同样与待替换的旧版回合场景比较。

## 4. 生成输入

后端发送给模型的生成输入必须包含：

```json
{
  "schemaVersion": "1.0.0",
  "session": {
    "sessionId": "session-id",
    "turnId": "next-turn-id",
    "sceneId": "scene-id",
    "summary": "截至上一轮的剧情摘要"
  },
  "world": {
    "activeEntries": []
  },
  "characters": [
    {
      "characterId": "character-id",
      "baseCard": {},
      "evolution": {},
      "currentState": {}
    }
  ],
  "relationships": [],
  "recentTurns": [],
  "activeStoryDirection": null,
  "playerInput": {
    "selectedChoiceId": null,
    "customChoice": null,
    "roleplay": null,
    "storyDirection": null
  }
}
```

模型不得获得任何供应商 API Key、内部数据库凭据或与当前会话无关的其他玩家数据。

### 4.1 虚构成人叙事与亲密内容

发送给模型的系统消息必须明确：游戏中的世界、事件和角色均为虚构。只有角色卡、世界书或当前状态**明确为成年人**的角色才能参与亲密或性相关情节；身份不明确的角色不得参与亲密内容。资料中明确为成年、且剧情与双方当前自愿共同支持时，可以直接延续亲密情节；不得仅因题材亲密而自动回避、说教、强制淡出、跳过关键互动或转写成无关剧情。原文参考中成年、自愿的亲密情节可以用于保持人物语气、情感张力、叙事细节和关系发展的连续性，但不得大段照抄，也不得把本剧本尚未发生的原作情节当作事实。

**重要信息传递**：线索、协议、秘密、关键对话等重要信息可能隐藏在包括亲密场景在内的任何场景中，模型必须完整描写场景内容以传递信息，不得因题材回避而删改、淡化、淡出、跳过关键互动或转成无关内容。

婚约、婚姻、过去关系、重生记忆、原作既有剧情或没有明确拒绝均不代表本轮同意。模型不得替玩家控制的角色同意、发起或完成玩家未输入的亲密行为；任何参与者拒绝或撤回同意时，不得升级亲密内容，应停在玩家可回应的节点。外部模型供应商自身的服务规则仍然适用。

本地程序不设成人内容安全边界，生成内容由所配置的 API 供应商输出审核自行甄别；本地仅保留上述虚构叙事定位与未成年人底线。

### 4.2 剧本方案一致性

普通 `sourceReferences` 仍只能从玩家设置的当前原作进度以内检索。程序还提供两类"导演引导"（统一以 `upcomingScriptGuidance` 进入请求，实际引用保存到 `generated_output_json.scriptGuidanceReferences` 并带 `scope` 标注）：

- **防剧透导演锚点（`next_chapter_director_only`）**：剧本任务处于活动状态、原文采用 `faithful` 且开启防剧透时，从每份原文的下一章节额外检索最多两个、总计不超过 3,600 字符；只约束重大方案和关键机制。
- **剧本推进引导（`next_chapter_progress_hint`）**：当剧情与剧本大纲保持一致（最近回合的 `storyDirectionEvaluation.continuity=aligned`；无活动剧情走向时仅在任务完成且对齐的窗口内）且原文开启防剧透时，从下一章节提取同样预算（最多两个、≤3,600 字符）的大纲方向提示，引导新剧情继续沿剧本推进。开局首回合、无原文或进度已到最后一章时不注入；剧情偏离（diverged/uncertain）或超过最近五个回合的完成判定不再注入。

两类引导都仅供叙事引擎使用：不能成为角色无条件知道的情报，不能被写成已经发生的事实，不能用于提前泄露与本轮无关的结果；剧情自然抵达时才按大纲推进，明显偏离或条件未满足时暂缓，不强行拉回剧本路线。页面不展开引导正文以避免剧透。

AI 控制角色提出会显著改变主线的治疗、解封、调查、营救、交易、作战或制度方案时，必须以已发生事实、当前任务、世界书、角色资料、普通原文片段或导演锚点为依据。若导演锚点已经明确核心机制、必要参与者、条件或因果，模型必须保留这些核心约束，不得自行发明另一名人物、机构、物品、地点或替代方案。玩家选择或已发生剧情导致条件变化时可以合理调整实现过程；依据不足时只能提出核验、试探或调查步骤，不能把臆测包装成确定可行的完整方案。

## 5. 生成输出总结构

模型必须只返回符合以下概念结构的 JSON，不得在 JSON 外附加解释、分析过程或思维链：

```json
{
  "schemaVersion": "1.0.0",
  "turn": {
    "scene": "本轮面向玩家的叙述",
    "events": [],
    "dialogue": []
  },
  "decision": {
    "context": "proposal_response",
    "prompt": "玩家需要回应的问题",
    "choices": []
  },
  "stateCommit": {
    "sceneTransition": {
      "locationId": "location-id",
      "locationName": "地点名称",
      "locationDescription": "地点资料",
      "presentCharacterIds": ["character-id"],
      "reason": "地点或阵容如此变化的原因",
      "evidence": ["event-id"]
    },
    "characterStateChanges": [],
    "relationshipChanges": [],
    "characterCardChanges": [],
    "worldBookChanges": [],
    "plotThreadUpdates": [],
    "plotTriggerUpdates": [],
    "storyDirectionEvaluation": null,
    "summaryPatch": ""
  },
  "warnings": [],
  "attributeChecks": []
}
```

所有变化数组都允许为空。没有变化时必须返回空数组，不得编造无意义修改。`attributeChecks` 是可选字段：没有属性判定时不返回该字段。

`sourceProgress` 是顶层的另一个可选字段：当本轮剧情实际发生的内容已推进到原文第 N 章对应的情节时，返回不小于 1 的整数 N（可跨章节推进）；对话、日常等未触及新章节的回合省略该字段。本地程序校验后只进不退地自动更新启用的原文文档进度（`current_chapter`），防剧透检索范围随之解锁；模型不得只为解锁后续章节而虚报进度。自动推进在普通回合、重生成与属性判定回填三条路径上一致生效，并写入只读的"剧情推进自动解锁"修改记录。

回合生成接口（SSE）在请求被客户端中断时发送 `cancelled` 事件：服务端在提交回合前检测到取消则不落库（回合数不变），前端收到后回到可编辑态；若取消发生在提交之后，以实际提交结果为准。非流式请求不受影响。

## 6. 剧情和对话生成

### 6.0 scene 充实度

`turn.scene` 是面向玩家的本轮叙述，应**完整充实**：写足本轮场景的环境与氛围、在场人物的反应与互动、玩家回应的直接结果与后续发展；单次文本量充分（上限 12000 字符），可写足细节与事件过程，不要只写两三句梗概。充实以本轮新发生的事实和进展为边界——充实不等于复述（规则 21）。

### 6.0.1 内心活动（characterThoughts）

`turn.characterThoughts`（可选，≤6 条、每条 ≤400 字符、characterId 必须存在）表达有内心活动的 AI 角色独白：想法是该角色的内在动机，影响其后续言行、决策与行动一致性（最近回合想法注入上下文保持跨回合一致）；**角色之间互相不知道对方的想法（玩家角色也不知道）**，正文、对话不得直接写出他人想法（读心等需剧情事件支撑），想法不自动成为言行。页面以折叠"内心活动"分区展示，历史回合回看同样可见。

### 6.1 事件

每个重要事件应包含稳定 ID、事件类型、参与角色、地点和已发生事实。事件必须描述已经发生的内容，不得把计划或可能性当成事实。

### 6.2 对话

每条对话必须标明说话角色。模型必须遵守角色的知识边界：

- 角色不能知道只存在于剧情走向输入中的导演意图。
- 角色不能知道自己未见证、未被告知且没有合理渠道获知的事件。
- 谎言和误解可以出现在对话中，但状态提交必须把它们标记为角色认知，而非客观世界事实。
- 模型不得替玩家角色编写关键承诺、决定或不可逆行为，除非玩家输入已经明确授权。

## 7. 候选选项生成

### 7.1 回应提议

当对方提出请求、交易、威胁、条件或合作时，`decision.context` 必须为 `proposal_response`。候选项从以下语义中按场景需要选择：

- `accept`
- `partial_accept`
- `reject`

候选项必须体现当前角色、风险和条件，而不是简单写成“接受”或“拒绝”。界面始终额外提供 `custom` 输入，不要求模型生成 `custom` 项。

### 7.2 决定行动

当剧情询问玩家下一步如何行动时，`decision.context` 必须为 `action_direction`。候选项应覆盖有实际差异的立场：

- `benevolent`
- `neutral`
- `malicious`

并非每轮都必须生成固定数量，但至少应提供两个真正不同的方向。界面始终额外提供 `custom` 输入。

### 7.3 跨轮选项差异

本轮 `decision.choices` 与最近 2-3 回轮的候选项应有**实质差异**（规则 33）：不得连续多轮出现"继续调查/观望/保持现状"式的近似选项；选项应随剧情进展与玩家回应结果变化（新的空间、新的代价、新的方向）。校验会产生**选项差异警告**（`normalizationWarning`，不拒绝回合、不触发修复重试）：本轮选项与最近 3 回轮候选项的 n-gram Jaccard 相似度 ≥ 0.65 时提醒"提供有实质差异的选择"，随回合警告入库。

## 8. 三种玩家输入

- **自定义选项**决定玩家如何回应当前决策。
- **角色言行**描述玩家角色在故事内说的话和做的动作。
- **剧情走向**是对 NPC 不可见的故事外导演目标。

三种输入可以同时存在。发生语义冲突时，优先级为：玩家明确的角色言行 > 自定义或已选候选项 > 剧情走向软约束。系统不得为了完成剧情走向而否定玩家本轮明确输入。

**角色想法（innerThoughts）**：玩家可随言行/选择一并提交角色内心想法（限长 1000 字符）。想法是玩家角色的内在动机——影响其言行风格、候选选项倾向与后续行动；**仅玩家角色自己知道，其他角色不可知**，正文、对话与事件不得直接写出他人想法（读心等需剧情事件支撑）；想法不自动成为言行。

**角色言行最高优先级**（系统消息规则 31）：玩家角色言行（说话/动作/言行输入）是当前回合最高优先级的故事事实——玩家角色说话时，在场 AI 角色必须回应其说的话（对话、反应、态度）；玩家角色行动时，必须呈现该动作的结果（事件、状态变化、世界反应）。玩家言行优先于 AI 候选选项与剧情走向：不得忽略、淡化或改写玩家角色言行，不得让剧情走向或后续剧本锚点覆盖玩家角色明确表达的行为；剧情走向仍是导演目标，但只能在承接玩家言行之后推进。近期回合中的玩家言行保持延续性：历史言行仍是角色关系、局势与人物记忆的依据，不得与已表达的行为前后矛盾。

**承接顺序**（规则 32）：玩家回应后的回合，`scene` 必须先完整呈现玩家回应的直接后果（NPC 的反应、动作结果、场景变化），再推进新的信息或事件；不得在玩家回应的结果被呈现之前，引入打断性新事件、新角色、新冲突或新选项。新信息应作为玩家回应结果的延续自然展开，而不是脱离玩家回应的独立插入。

上下文结构为玩家言行提供高亮与标注：`context` 顶层新增 `latestPlayerRoleplay`（`{ mode: "speech"|"action"|"mixed", content }`，仅本轮有言行时出现，置于上下文最前，与 `playerInput.roleplay` 内容一致）；近期回合（`recentTurns`）每回合的 `playerInput` 可携带 `mode` 标注（有言行时输出），帮助模型识别历史言行的性质并保持行为一致性。

## 9. 地点与出场阵容同步

每轮必须返回 `sceneTransition`，表示该回合结束时的权威场景状态：

- `locationId`：已有地点必须沿用原 ID；剧情发现的新地点使用稳定的新 ID。
- `locationName` 与 `locationDescription`：新地点必须提供，已有地点的信息以本地资料为准。
- `presentCharacterIds`：回合结束时仍在当前场景内的全部启用角色，必须包含玩家角色。
- `offstageUpdates`（可选）：不在场角色的所在地点变化（返回宅邸、前往城外等）。目标角色不得同时出现在 `presentCharacterIds`；进入已有地点沿用其 ID，进入新地点必须提供 `locationName`（可带 `locationDescription`）。
- `reason` 与 `evidence`：必须能指向本轮真实发生的事件或对话。

后端根据上一轮状态和 `presentCharacterIds` 的差集自动生成人物加入、离场与位置变化。普通 `characterStateChanges.patch` 禁止包含 `present` 或 `locationId`，避免同一轮出现冲突的出场结论。玩家手工移动地点时使用地点的默认登场阵容；剧情生成可以根据实际事件覆盖本轮最终阵容，但不会改写地点的玩家设定。

**地点一致性**：正文、事件描写的场景地点必须与 `sceneTransition` 一致——场景移动时 `locationId` 必须指向正文实际到达的地点（已有地点沿用其正确 ID，不得把正文地点填成另一已有地点的 ID；新地点 `locationName` 必须与正文地点名一致）；未发生场景移动的回合（对话、行动、决策）不得随意改动 `locationId`，沿用上一轮 ID。校验产生**地点一致性警告**（`normalizationWarning`，不拒绝回合、不触发修复重试）：仅当本轮 `locationId` 与上一轮不同（场景确在移动）且正文或事件摘要中出现与目标地点不同的已知地点名时触发，随回合警告入库并在页面"本轮变化-模型提示"展示；对话中单纯提及别处或场景未移动时不警告。

## 9.1 游戏内时间

`session_state.core.gameTimeDay` 表示游戏内第几天，开局为第 1 日。游戏内时间只由剧情推进驱动：`sceneTransition` 可以通过 `gameTimeDayNext`（可选整数，本回合结束日期，不得小于当前日）**显式声明**本回合结束时的日期，或通过 `timeAdvance`（`moment`/`hours`/`one_day`/`several_days`）声明时间幅度——两者都提供时日期一律以 `gameTimeDayNext` 为准（实际推进 = `gameTimeDayNext − 当前日`），语义冲突只产生警告不拒绝回合；只提供 `timeAdvance` 沿用既有语义；都不提供时日期不变（相当于 `moment`）。跨日剧情（正文出现"次日""数日后"等时间流逝）必须声明日期，正文时间短语与日期一致。任务 `deadlineDay` 到期后，`expiredDeadlines` 作为导演级硬事实注入上下文，模型必须让期限后果在本轮显现；期限只会在剧情时间实际推进到该日之后到期。

**剧情约定（appointments）**：剧情中角色之间明确约定的未来时间点（会面、交易、交付、赴考等剧情内事件，区别于剧本包预埋任务的 `deadlineDay`）由模型在 `stateCommit.appointments` 登记：`{ id, title, description, characterIds?, atDay }`（完整数组替换，`null` 清除全部，省略保持不变）。物化为 `appointment` 状态实体（pending）。未到期（`atDay` 大于当前日期）的约定进入上下文 `appointments`（含剩余天数），剧情可自然引用；到期（`atDay` 不超过当前日期）且未处理的约定以 `dueAppointments`“约定日已到”硬事实注入，模型必须在剧情中体现兑现或失效（如期赴约、错过、变故、重新约定）并同步更新；五回合一天模式下 `atDay` 同样按游戏内日期计算（一天 = 5 个回合）。

`session_state.core.timeMode` 选择时间推进方式（缺省 `story`，**新建剧本时确定**——开局表单单选或剧本包 `adventure.timeMode` 可选声明预填，开局后不可切换）：`story` 为剧情驱动（上述语义）；`turn_based` 为五回合一天——每个回合固定推进一个时段（早上→上午→中午→下午→晚上，按 `phaseOffset % 5` 取 `DAY_PHASES`），每 5 个回合进入下一天（`gameTimeDay +1`），模型不得声明 `timeAdvance`/`gameTimeDayNext`（会被忽略），时间短语一致性警告在 `turn_based` 下不触发；任务期限与状态词条到期按天自动生效（一天 = 5 个回合）。上下文在 `turn_based` 下注入 `currentDayPhase` 与 `timeMode`。切换模式保留当前游戏内日期，切换后从"早上"开始重新计时。

校验会产生**时间短语一致性警告**（`normalizationWarning`，不拒绝回合）：正文或事件摘要出现"次日/翌日/数日后/几天后"等时间短语而本轮未声明日期推进（`gameTimeDayNext` 缺省且 `timeAdvance` 为 moment/hours/缺省）时触发，提示模型用 `gameTimeDayNext` 声明结束日期；"数小时后"类不视为跨日。

任务期限有系统确定性兜底：`deadlineDay` 到达当天仍 active/queued 未完成的任务，在回合提交时由系统标记为 `expired` 终态（记录 `expiredAtTurnId` 与 `expiryReason`），退出活动任务集合——不再作为当前任务注入、不再作为接续/推荐对象，剧情任务管理中不可再编辑或切换；`expiredDeadlines` 提示注入保留，剧情后果仍由模型在硬事实提示下显现，不自动编造。与偏离触发器 `deadline` 的强制 fire（系统应用后果）不同，任务兜底只做状态确定性标记；本轮剧情实际完成任务时以完成状态为准，不重复标记。

## 10. 角色当前状态变更

每项角色状态变更必须包含：

- `characterId`：已存在的角色 ID。
- `patch`：只包含需要改变的字段。
- `reason`：为什么发生变化。
- `evidence`：对应的本轮事件、动作或对话 ID。
- `duration`：`instant`、`scene`、`until_changed` 或 `permanent`。

示例：

```json
{
  "characterId": "captain-lin",
  "patch": {
    "condition": ["left-arm-wounded"],
    "mood": "guarded"
  },
  "duration": "until_changed",
  "reason": "角色在北门交战并受伤",
  "evidence": ["event-12"]
}
```

如果角色死亡或失去行动能力，必须同步更新其状态。人物加入、离场和地点变化统一通过 `sceneTransition` 提交。

### 10.1 角色属性（attributes）

`character_state.attributes` 保存角色属性（0-100），白名单为：力量、敏捷、感知、意志、魅力、智力、体质。事件驱动的属性变化通过 `characterStateChanges` 的 `attributes` 对象写入最终数值（0-100）；后端校验白名单与范围，越界值会被拒绝或钳制。属性未设定时按 50 计。

### 10.2 行动受限（restriction）

`character_state.restriction` 表达角色因死亡、被关押、被控制、被束缚等"行动受限"因素无法自由行动：`{ kind: "dead" | "imprisoned" | "controlled" | "bound" | "other"; summary: string; sinceTurnId?: string }`。模型通过 `characterStateChanges.patch.restriction` 设置（对象）或解除（`null`），后端校验 kind 白名单、summary 长度与结构。

行动受限角色在解除前受到**硬拦截**（整轮校验拒绝并走修复重试）：

- 不能出现在 `turn.dialogue.speakerId`（不得替其发声）；
- 此前不在场的受限角色不能被加入 `sceneTransition.presentCharacterIds`（已在场的保留在阵容中放行，如遗体留在现场）；
- 不能出现在 `sceneTransition.offstageUpdates`（不得自由移动）；
- 不能出现在 `attributeChecks`（不得发起属性判定）。

解除必须伴随真实剧情事件（复活、越狱、挣脱控制、释放等）写入 `turn.events`，并在**同一回合**通过 `characterStateChanges` 把该角色 `patch.restriction` 置为 `null`；未同轮解除的发言/登场/移动/判定全部拒绝。玩家可在人物管理中设置或解除行动受限，设置的 `sinceTurnId` 记录当时分支头回合。

### 10.3 状态词条（statuses）

`character_state.statuses` 记录角色身上的 buff/debuff 词条（受伤、中毒、增益等）：`{ id, name, kind: "buff" | "debuff", hidden?: boolean, description, sourceTurnId?, expiresAtDay? }`。模型通过 `characterStateChanges.patch.statuses` 以完整数组替换（`null` 清除全部），后端校验 id 唯一、kind 白名单、长度与范围。

- **隐藏状态**：`hidden: true` 的词条以导演级"未察觉状态"（`hiddenCharacterStatuses`）注入，角色未察觉前模型不得在叙述、对话或思考中点破；角色通过剧情行动（检查伤口、求医、观察症状、探索）实际认识到后，在同一回合把该词条 `hidden` 置 `false`，之后作为正常可见状态。
- **到期移除**：`expiresAtDay` 不超过当前游戏内日期时，系统在回合提交事务内自动移除该词条并写入状态变化记录（剧情驱动的到期/恶化语义由模型在剧情中体现并更新词条）。
- **剧情联动与行为倾向**：debuff 随时间或剧情恶化或恢复，并体现在叙述与词条内容中；角色身上存在 debuff 且有可行解决方案时，角色行动与候选选项应倾向解决（求医、解毒、治疗、休息等）；属性判定应结合词条判断合理性（不修改判定公式）。
- **状态一致性**：正文、事件、对话中出现的任何状态变化（恶化、恢复、新增、解除、症状显现）必须同步写入本轮 `patch.statuses`（更新 description、调整 `expiresAtDay`、移除或新增词条），不得只在叙述中暗示；未变化的词条保持原 id 与原内容。
- **跨日状态演化**（规则 29）：`timeAdvance` 为 `one_day` 或 `several_days` 时，必须逐角色检查所有进行中的词条——debuff 按剧情演化并更新 description 与 `expiresAtDay`（延长、提前、解除后移除），buff 判断消退或延续；时间推进后必须演化词条，不能沿用旧内容。
- **剩余天数对照**：上下文角色词条每项附带计算字段 `daysRemaining = expiresAtDay − gameTimeDay`（负数表示已到期、提交时由系统移除），并统一注入 `currentGameTimeDay`——纯上下文计算，不落库、不改协议。
- **一致性警告**：若本轮 `scene` 或 `events` 文本出现某角色可见词条的名称或描述关键词，而该角色本轮 `patch.statuses` 未更新该词条 id（且未显式清除全部），校验产生一条 `normalizationWarning`（不拒绝回合），随回合警告入库并在页面"本轮变化"区域展示"模型提示"。
- 剧本包可通过 `adventure.initialStatuses` 声明人物开局状态词条（`characterName` + `statuses`，字段与本节一致，可含 `hidden`），开局物化为各角色 `character_state.statuses`，隐藏词条沿用上述导演级注入与探索解锁语义。

### 10.5 角色已知信息（knownFacts）

`character_state.knownFacts`（可选）记录角色已经知道的重要信息：`[{ id, content }]`（完整数组替换，`null` 清除全部；id 稳定唯一 ≤120 字符、content ≤300 字符）。模型在角色获知重要信息时（对话告知、信件、发现、偷听等）登记到该角色 `knownFacts`；**已登记的信息，后续剧情不得重复生成"首次获知/得知该信息"的表述**——剧本推进到相关情节时应体现角色已掌握信息（基于信息行动、决策、回应），不重复交代获知过程；信息按角色隔离（A 已知不等于 B 已知，除非 B 也获知并登记）。上下文按角色注入已知信息（每角色 ≤10 条、总预算约 1200 字符，超出保留最近登记）。

### 10.4 关系变化（relationshipChanges）

`stateCommit.relationshipChanges` 更新角色之间的关系数值：每项包含 `sourceCharacterId`、`targetCharacterId`（均为已存在角色）、`dimension`（`trust`/`affection`/`fear`/`hostility`/`respect`）、`delta`（-100 ~ 100）、`reason` 与 `evidence`。后端按维度对累加并钳制到 -100 ~ 100，自动建立或更新双向关系记录。`evidence` 至少 1 条且必须指向本轮或历史真实事件/对话 ID。关系变化必须**明确区分维度**（规则 37）：信任（trust：托付秘密、可靠承诺、守约）与好感（affection：心动、亲近、思念）是不同维度，情侣/暧昧关系深化时必须判断本次加深的是信任、好感还是两者兼有（兼有时分别登记两条变化，各自 `delta` 与 `reason`），不得笼统"关系加深"；`reason` 必须指向具体事件或对话依据。

## 11. 角色卡演化变更

角色卡变更必须满足“已经发生、影响长期扮演、不是短期状态”三个条件。

每项变更必须包含：

- `characterId`
- `operation`：`add`、`update` 或 `deactivate`
- `path`：角色演化层中的目标字段
- `value`：新值；`deactivate` 时可以省略
- `reason`
- `evidence`
- `sourceTurnId`

允许自动写入的路径限定为：

- `identity.titles`
- `identity.affiliations`
- `goals.longTerm`
- `beliefs`
- `fears`
- `vows`
- `permanentConditions`
- `abilities`
- `revealedSecrets`
- `relationshipMilestones`

模型不得直接生成针对 `system_prompt`、`post_history_instructions` 或未知扩展字段的自动补丁。

角色卡变化默认写入会话演化层，并立即影响后续角色扮演。永久合并到可导出的 Tavern Card V2 前必须由玩家确认。

## 12. 世界书变更

世界书变更支持：

- `create`：新增持久世界事实。
- `update`：更新已有事实。
- `deactivate`：旧事实已失效但需要保留历史。

每项变化必须包含来源回合、原因和证据。模型必须优先更新或停用冲突旧条目，避免新旧事实同时触发。

世界书变化自动写入当前会话动态层。`base` 与 `base_import` 都属于不可变基础层，模型更新或停用它们时必须建立带 `shadowsEntryId` 的 `session_overlay`，不得原位修改。玩家在工作台编辑基础条目时建立 `player_override`，界面逐字段展示差异；停用与软删除仍保留活动遮罩，只有“恢复基础版本”才撤销遮罩。

## 13. 剧情走向生命周期

剧情走向保持 `active`，直到发生以下情况之一：

- 玩家用新走向替换它。
- 玩家取消或清空它。
- 已经发生的剧情满足了该走向。

完成评估必须返回 `status`、`reason`、`evidence`、`continuity`、`continuityReason`、`recommendedModuleId` 和 `suggestedNextDirection`。只有能够引用已发生事件或对话时才能标记 `completed`。

- 未完成时，`recommendedModuleId` 和 `suggestedNextDirection` 都必须为 `null`。
- 完成且 `continuity=aligned` 时，可从前置任务已完成、`autoContinue=true` 且当前事实满足启用条件的预埋任务中返回一个 `recommendedModuleId`。
- 偏离剧本、连续性不确定或没有合适预埋任务时，`recommendedModuleId=null`，并在 `suggestedNextDirection` 中返回 `title`、`content` 和 `reason`。
- `recommendedModuleId` 与 `suggestedNextDirection` 必须互斥。若供应商仍同时返回，程序在连续性对齐且推荐任务确实可用时采用预埋任务；否则忽略推荐任务并采用自然生成的新目标。该确定性消歧会写入本轮警告，不触发整轮丢弃。
- 玩家手动替换或取消剧情走向时，玩家输入始终优先，当前预埋任务记为已偏离，不能用任务链覆盖玩家目标。

### 13.0 偏离路线处理与候选选项引导

当 `continuity=diverged`（剧情明显偏离剧本路线）时，系统在生成输入中注入导演级"偏离状态清单"（`divergenceSignals`，只进入本轮请求与上下文快照，不进历史回合、不展示玩家），并启用"偏离路线处理规则"：

- **偏离状态清单**分为两组：`broken`（已破坏的原作触发条件：已过期任务、已触发的偏离触发器、被停用未完成任务、离场或停用的关键角色、停用地点）与 `recoverable`（仍可满足：未触发触发器、进行中的活动任务、未回收伏笔）。它只供叙事引擎判断方向，不是角色自动知道的情报。
- **防原地打转**：偏离状态下每个候选选项都必须对局势有实质推动（改变关系、推进目标、承担代价或产生新的可验证结果），禁止连续两轮全部是调查或观望类选项。
- **两个自然方向**（选项措辞不得出现"坏结局/bad end/放弃原作/跳过剧情"等字样）：
  - 方向一（滑向坏结局）：孤注一掷、极端手段、接受代价、押上一切等选择；`divergenceState.badEndDrift=rising` 时可增加该方向选项。
  - 方向二（另辟蹊径完成原目标并略过原作后续）：使用当前已建立的关系、资源与证据达成目标；`outlineRecoverable=broken` 时选项自然体现另起炉灶不再回头，`recoverable` 时保留沿原作路径继续的可能。
- **规则 20 例外**：偏离状态下的替代方案可以基于已发生事实与当前资源提出（不再强制"只能调查"）；对齐或不确定状态恢复原约束。

`storyDirectionEvaluation` 可选的 `divergenceState` 字段（`outlineRecoverable: "recoverable" | "broken"`、`badEndDrift: "rising" | "neutral"`、`reason`）**仅在 `continuity=diverged` 时可填写**，用于模型结构化报告原作后续触发条件是否已不可满足与坏结局倾向，系统据此调节引导强度；该字段是导演级输出，不展示给玩家。

完成旧走向、更新当前任务状态和启用新走向必须在同一回合事务内提交。预埋任务只是导演意图，不是 NPC 知识，也不得当作尚未发生的既定剧情。

剧情走向完成时不一定修改角色卡或世界书；是否修改取决于完成它的事件是否产生了角色长期变化或持久世界事实。

### 13.1 伏笔（plot_thread）生命周期

剧本包可通过 `adventure.foreshadowing` 声明伏笔（`id`、`keywords`、`seedCondition`、`payoffCondition`、`payoffSummary`，可选 `characters`）。开局物化为 `plot_thread` 实体，状态为 `dormant`：

- **埋设（seed）**：当本轮剧情自然满足某伏笔的 `seedCondition`（如角色进入相关地点、遭遇相关人物或关键物件），模型把伏笔含蓄地埋入叙述（NPC 不应察觉其目的），并在 `stateCommit.plotThreadUpdates` 中报告 `{"threadId": "...", "operation": "seed"}`；后端把状态改为 `seeded` 并记录 `seededAtTurnId`。
- **进入上下文**：已埋设的伏笔获得高优先级，与当前输入相关的未埋设伏笔也按关键词相关度进入上下文（`rankedStates` 权重加成）；提示词中的 `plotThreads` 分区携带 `payoffCondition` 与 `payoffSummary`。
- **回收（payoff）**：当剧情自然抵达某伏笔的 `payoffCondition` 时，模型必须在叙述中呈现 `payoffSummary` 的核心信息，并在 `plotThreadUpdates` 中报告 `operation: "payoff"`；后端把状态改为 `paid_off` 并记录 `paidOffAtTurnId`。不得提前泄露或把尚未回收的伏笔当成既定事实。
- 校验规则：`seed` 只允许 `dormant` 状态，`payoff` 只允许 `seeded` 状态；`threadId` 必须存在；`evidence` 必须引用真实事件或对话。

### 13.2 偏离触发器（plot_trigger）生命周期

剧本包可通过 `adventure.triggers` 声明偏离触发器（`id`、`when`、`consequence`，可选 `stateEffects` 与 `deadline`）。开局物化为 `plot_trigger` 实体，状态为 `armed`：

- **触发（fire）**：当本轮剧情满足某触发器的 `when` 条件时，`consequence` 必须作为“意外阻碍”真实写入本轮事实（不得因为后果严厉而回避或淡化），并在 `stateCommit.plotTriggerUpdates` 中报告 `{"triggerId": "...", "operation": "fire"}`；后端把状态改为 `fired` 并记录 `firedAtTurnId`。
- **强制状态影响**：`stateEffects` 由系统在报告 `fire` 后确定性应用：`relations` 按角色姓名调整关系值（trust/affection/fear/hostility/respect，-100 ~ 100）；`attributes` 直接设定角色属性（白名单 0-100）；`flags` 中的 `bad_end` 在会话状态置位 `badEnd`，游戏页显示“结局警示”横幅。模型不得自行改写这些数值。
- **期限（deadline）**：`deadline` 表示最迟必须在游戏内第几天前生效；超过期限后系统在回合提交时强制触发（`fireReason` 记录“期限已至”），后果与状态影响照常应用。
- 校验规则：已 `fired` 的触发器不能重复触发；`triggerId` 必须存在；`evidence` 必须引用真实事件或对话。

### 13.3 属性判定（attributeChecks）与骰子结算

当玩家角色或在场角色进行有明显成败可能的关键行动（潜行、说服、对抗、搜索、拆解、战斗动作等）时，模型可以在输出顶层提议属性判定：

```json
"attributeChecks": [{
  "id": "check-1",
  "characterId": "character-id",
  "attribute": "敏捷",
  "difficulty": 70,
  "context": "在不惊动守卫的情况下撬开旧锁"
}]
```

- 模型只提议“何时判、用什么属性、多难”，**不自行写出判定结果**；每轮最多 4 项，属性必须是白名单内名称，难度必须是 1-100 整数。
- 回合生成结果含判定请求时**不立即落库**：回合进入待确认草稿（`pending_turns`），分支头保持不变，界面弹出“属性 vs 难度 + 骰子”面板。
- 玩家掷骰（可重掷）并确认后，后端 `lib/story/判定服务.ts` 确定性结算：`|属性−难度| ≥ 30` 时实力悬殊直接判定（成功/失败，无需掷骰）；否则按 `最终值 = 属性 + d100 × 30%` 与难度比较，`最终值 ≥ 难度` 为成功，`最终值 ≥ 难度 − 10` 为部分成功，否则失败。
- 结算结果作为已发生事实事件（`attribute-check:<checkId>`）回填该回合，追加一条叙述消息，并把判定记录物化为 `plot_check` 状态实体进入状态审计（可在历史回看中查看）；不重新生成叙述。
- 玩家可以跳过全部判定（记为“放弃判定”），回合仍会提交。重复确认按幂等处理；分支头变化后确认会返回冲突错误。
- 角色属性随剧情变化通过 `characterStateChanges` 的 `attributes` 对象更新（0-100 绝对数值，白名单校验）。

## 14. 变化归类规则

| 变化 | 保存位置 | 示例 |
| --- | --- | --- |
| 单轮叙述或普通对话 | 回合记录 | 角色询问玩家姓名 |
| 短期、即时或场景内变化 | 角色当前状态 | 紧张、受轻伤、正在逃跑 |
| 角色长期且稳定的变化 | 角色演化层 | 加入阵营、立下誓言、永久失明 |
| 多角色共享的持久世界事实 | 动态世界书 | 王国易主、城市被毁、法律改变 |
| 两个角色之间的数值或立场变化 | 关系状态 | 信任降低、敌意增加 |
| 对后续故事的玩家导演目标 | 剧情走向状态 | 希望剧情转向调查失踪案 |

剧本包可以通过 `adventure.initialRelationships` 声明开局关系基线（按角色姓名引用，各维度 -100 到 100），开局时建立对应关系状态；未声明的角色关系保持中性（0）并标记“关系尚未建立”。

剧本包可以通过 `adventure.locations` 预注册剧本中可能出现的地点（名称、描述、常驻角色与重要性标记），开局即建立地点实体；未预注册的地点仍可在剧情中动态建立。`adventure.storyModules` 中的任务可以声明 `deadlineDay`（游戏内期限），到期后每回合注入期限已至的硬事实，模型必须让后果在剧情中显现。剧本包还可以通过 `adventure.foreshadowing` 与 `adventure.triggers` 声明伏笔和偏离触发器（见 13.1、13.2）。

一次事件可以产生多种变化。例如“角色在政变中成为新国王”应同时更新角色当前状态、角色演化层和世界书。

## 15. 后端校验规则

保存前必须验证：

1. JSON 能够解析且 `schemaVersion` 受支持。
2. 所有角色、世界书条目、回合和事件引用均存在。
3. 所有补丁路径位于允许列表中。
4. 每项持久变化都有原因和证据；证据至少 1 条且必须指向已发生事件或对话 ID（角色状态、关系、角色卡、世界书、伏笔与触发器更新均适用），否则整轮拒绝并走修复重试；剧情走向评估未完成（active）时可以没有证据。
5. 角色没有使用超出知识边界的信息。
6. 角色卡变化与世界书变化没有把计划、谎言或猜测写成客观事实。
7. 同一提交中不存在相互矛盾的新增和更新。
8. 剧情走向完成判断能够引用实际事件。
9. 不含 API Key、内部提示词或思维链内容。
10. 状态提交全部通过后再一次性写入存储。

校验失败时，后端应该携带简短错误列表要求模型仅修复结构化结果；不得让模型重新自由改写已经展示给玩家的剧情，除非剧情本身也不合法。

## 16. 玩家可见的变更记录

每轮结束后，界面可以折叠显示：

- 哪些角色状态发生了变化。
- 哪些角色卡演化项被新增或更新。
- 哪些世界书条目被新增、更新或停用。
- 哪些伏笔被埋设或回收、哪些偏离触发器被触发。
- 当前剧情走向是否仍然有效或已经完成。
- 本轮的属性判定请求与掷骰结算结果。

玩家必须能够撤销尚未进入下一轮的状态提交。基础世界书不做破坏性永久合并；玩家通过可编辑、可停用、可恢复的修订覆盖层确认长期修改。

## 17. 最新回合重生成

重生成只能作用于当前分支最新且由模型生成的回合。玩家必须提供非空的修改意见（**日期修正模式除外**，见下），系统应将其作为本次重写偏好单独注入提示词，但不得允许它覆盖系统规则、世界书、角色卡、父回合结束状态或结构化输出协议。重生成必须复用原来的玩家输入，并从父回合结束状态重新生成；旧版输出可以作为明确标记、不可信且尚未发生的“待替换草稿”供模型定位修改对象，但不得注入为历史事实，也不得追加一个新回合来伪装替换。

重生成请求可携带可选 `mode`（`"standard"` 缺省 / `"time_fix"`）：日期修正模式下修改意见可留空，系统注入"日期修正重写指令"——检查待替换回合正文的时间流逝暗示（次日、数日后、约定到期等），若正文暗示而旧版未声明日期，重写必须设置 `gameTimeDayNext` 使正文与日期自洽；正文无流逝则保持日期不变，不得虚构时间流逝。该模式下若重写结果仍出现时间短语而日期未推进，时间短语一致性警告**升级为校验错误**（走修复重试）。五回合一天模式下日期由回合固定推进，time_fix 提示不得声明 `timeAdvance`/`gameTimeDayNext`，日期变化通过继续推进回合实现。

玩家可以要求调整、删除、替换或重排待替换回合中由 AI 控制的角色与 NPC 的动作、台词、态度、事件顺序、场景结果、状态变化和候选项。模型不得以“不能控制他人”“必须保持原剧情”或“旧版动作已经发生”为由拒绝；玩家角色原始输入仍不可由模型擅自改写。若意见与更早事实或角色卡存在张力，模型应在保留玩家控制权的前提下生成最贴近意见且具有人物逻辑的版本。

替换前必须确认分支头、父回合和重生成版本均未变化。新输出应执行与普通生成完全相同的结构、引用和证据校验；校验通过后，叙述、对话、事件、状态变化和当前物化状态必须在同一事务中替换。旧版结构化结果应进入独立审计记录。任何生成失败、版本冲突或玩家手工状态保护都必须让当前剧情保持原样。

## 18. 供应商可用性与剧情边界

模型目录读取和可用性审核属于本机设置操作，不是剧情回合。目录读取不得建立剧情、修改人物或写入 SQLite；完整审核只发送固定的最小 JSON 测试消息，不能携带世界书、角色卡、原文、玩家输入或历史剧情。审核失败、超时或协议不兼容不得改变当前剧本状态。

模型目录可见不等于 token 拥有生成权限。只有所选模型完成实际 Chat Completions 请求并返回预期 JSON 后，界面才能标记本次审核通过；审核结果不得推断目录中其他模型同样可用。切换供应商、Base URL、API Key、模型或 JSON 输出方式后，旧审核立即失效。

## 19. 创建前的原文资料生成

原文生成剧本包与剧情回合输出共享模型供应商适配器，但不共享回合协议或数据库事务。玩家明确上传的文本必须标记为不可信资料；短文可以完整进入请求，长文只能发送受预算限制、覆盖开篇与全书分布的代表片段。

流程必须分为两个明确阶段。分析阶段只允许返回候选人物、推荐的玩家/主要 AI 角色，以及带章节、地点、摘要和在场人物的开场候选；不得修改当前开局表单。玩家确认两名不同角色和一个开场后，正式生成阶段才允许返回人物、世界事实、剧情任务和开场蓝图。两个阶段分别最多修复一次，不能把一次分析结果直接当作正式剧本包。

正式生成不得更换玩家确认的人物分工或开场章节。输出必须携带 `opening.sourceChapterIndex`；本地程序必须核对它与确认值一致，并把选定章节保存为原文参考的当前进度。模型不生成数据库 ID，不直接写入 SQLite，也不能把原文中的指令提升为系统规则。本地程序必须完成以下确定性工作：

- 生成 Character Card V2、世界书与剧本包版本字段；
- 建立稳定且唯一的世界书与任务 ID，以及无环前置关系；
- 原样内嵌玩家上传的完整原文并默认开启防剧透；
- 保护玩家角色的言行、同意、承诺和感情决定权；
- 使用正式剧本包导入器再次校验结果。

只有最终包通过完整校验后，浏览器才可以原子替换当前开局草稿；任一失败都不得清空旧表单或建立半成品剧本。分析数据和待生成原文只保存在当前页面内；刷新后可以丢弃，但不能被误认为已保存剧本。角色在场状态、世界书和任务链必须保持可编辑，并提示玩家在创建前确认。

对已通过校验的生成包，玩家可以选择角色资料、世界书、剧情任务或开篇中的一个分区，并提交不超过 2,000 字符的必填修改意见。分区重生成仍以完整原文代表样本和已确认人物、开场章节为硬约束；当前分区内容必须标记为不可信资料。模型返回完整候选蓝图，本地程序只合并目标分区，禁止附带修改非目标分区或原文参考。任务分区需要同步有效的首任务引用，开篇分区必须保留当前任务链引用。合并后必须再次执行完整包校验；成功结果先进入待确认态，按项目展示当前值、新值和新增/移除/修改状态。只有玩家明确采用后才刷新目标字段和下载基线；放弃、校验失败或预览基线已经变化时，所有表单和已采用生成基线保持原样。

## 20. 版本与兼容

- 输入和输出都必须携带 `schemaVersion`。
- 新增可选字段可以提升次版本号。
- 删除字段、改变字段语义或改变补丁路径必须提升主版本号。
- 未识别的角色卡和世界书扩展字段必须原样保留，不得在导入导出过程中丢失。
