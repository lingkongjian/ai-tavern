# 人物卡、世界书、剧本包与完整存档标准

版本：`1.5`

本标准用于以下场景：

1. 玩家从其他酒馆软件导入已有 JSON 文件；
2. 玩家手工编写人物卡或世界书；
3. 让 AI 生成可以直接导入本项目的文件。

导入模式包括开局剧本包、单张人物卡、世界书、剧情中的原文参考和完整运行存档。开局剧本包适合分享尚未游玩的第一幕设定；完整存档适合迁移已经产生回合、分支和动态状态的故事；人物卡和世界书模式适合对当前表单逐项补充；原文参考在剧本创建后从游戏页导入。

制作和发布资料时，请先阅读 [《导入材料文件结构指导手册》](../public/文件标准/导入材料文件结构指导手册.md)。手册区分可直接导入的单文件包、作者维护用的拆分目录和程序生成的完整运行存档，并给出推荐目录、组装流程与发布检查清单。

导入入口位于新建战役页面的“导入或生成剧本资料”。普通文件先在内存中解析和预览；原文自动生成先调用当前模型分析人物与开场候选，玩家确认分工后才再次调用模型得到结构草稿，再由程序组装并校验成同一种标准剧本包。只有玩家最终创建战役时，当前表单才会与开场回合一起原子写入本地 SQLite。

## 通用限制

- 编码：UTF-8。
- 格式：单个 JSON 对象，不接受 Markdown 代码块或 JSON 前后的解释文字。
- 后缀：`.json`。
- 单文件大小：不超过 1 MB。
- 完整剧本包因内嵌多个文件，单文件不超过 5 MB。
- 完整运行存档因包含全部历史、原文和检索切片，单文件不超过 100 MB。
- 开局最多 1 名主要 AI 角色、20 名其他 AI 角色。
- 开局导入的世界书条目总数不超过 200 条。
- 每个剧本最多保存 5 份原文参考，每份不超过 200 万字符，支持 UTF-8 `.txt` 和 `.md`。
- 空正文条目会被跳过；完全没有有效条目的世界书会被拒绝。
- 普通 JSON 导入不会调用 AI 模型；“AI 原文分析”和确认后的正式生成都会调用当前模型并消耗 API 额度。

## 完整剧本包标准

完整剧本包使用 `ai_tavern_adventure_bundle_v1`，把原本需要分别选择的资料放在同一个 JSON 中：

- 战役名称、说明和世界观概要；
- 玩家人物卡；
- 主要 AI 角色人物卡；
- 最多 20 名其他 AI 角色人物卡；
- 一份最多 200 条的世界书；
- 开场地点、开场场景和初始剧情走向。
- 可选的 `referenceDocuments` 原文参考数组。
- `1.1` 版可选的 `storyModules` 剧情任务链，以及 `opening.initialStoryModuleId` 开场任务 ID。`1.0` 包仍可导入。

`storyModules` 最多 30 项。每个任务包含稳定唯一的 `id`、`title`、对 NPC 不可见的 `objective` 和至少一项 `completionCriteria`，并可设置：

- `activationConditions`：剧情事实需满足的启用条件；
- `prerequisiteModuleIds`：必须先完成的任务 ID；
- `continuityNotes`：哪些剧情分支仍可视为没有脱离原剧本；
- `autoContinue`：是否允许在当前目标完成后自动接续，默认 `true`；
- `deadlineDay`：任务期限（游戏内第几天前完成）。到期后后续回合会注入期限已至的硬事实，剧情必须让后果显现。

任务顺序不等于强制线性剧情。只有完成证据、前置任务、启用条件和剧情连续性同时支持时，系统才会接续预埋任务。如果玩家已把故事带向其他路线，系统会保留任务历史，并沿当前已发生剧情生成新目标，不会强行拉回原作。

`1.1` 版剧本包还支持两个可选分区：

- `initialRelationships`：开局角色之间的初始关系基线（最多 100 条）。每项使用 `sourceCharacterName` 与 `targetCharacterName`（必须与角色姓名一致），`dimensions` 提供 `trust`、`affection`、`fear`、`hostility`、`respect`（-100 ~ 100，缺省为 0；`affinity` 作为好感维度的旧别名仍可导入，新内容一律写 `affection`），`summary` 概括关系性质（如“青梅竹马”“名义上的未婚夫妻”）。开局物化时自动建立双向记录（A→B 与 B→A 独立演化）；声明中已显式给出反向的以声明为准。
- `locations`：剧本中可能出现的地点清单（最多 60 个）。每项包含 `name`、`description`，可选 `characters`（默认在该地点活动的角色姓名）与 `important`（重要地点，更高优先级进入上下文）。开局即预注册为地点实体，未进入前就被声明；与开场地点同名的声明会被跳过。
- `foreshadowing`：跨章节伏笔清单（最多 30 条）。每项包含 `id`、`keywords`（稳定关键词，至少 1 个，相关时刻把伏笔带进上下文）、`seedCondition`（伏笔埋入剧情的出现条件）、`payoffCondition`（回收条件）与 `payoffSummary`（回收时应呈现的核心信息），可选 `characters`（密切相关的主要角色姓名）。开局物化为 `plot_thread` 实体；出现条件满足时模型报告 `seed` 埋入，回收条件满足时报告 `payoff` 并呈现概要。它与剧情任务互补，解决短上下文下跨章节伏笔真正目的丢失的问题。
- `triggers`：偏离触发器清单（最多 30 条）。每项包含 `id`、`when`（触发条件描述）与 `consequence`（条件满足后必须显现的意外阻碍），可选 `stateEffects`（关系/属性/标志影响，由系统在触发后强制应用；`flags` 中的 `bad_end` 会置位结局警示横幅）与 `deadline`（期限，游戏内第几天前必须生效，超过后系统强制触发并应用后果）。示例场景：主角弱小时强闯反派地盘 → 强大反派提前登场；已婚状态下与异性接触 → 正主怀疑、敌我关系大幅转变。

`referenceDocuments` 中每项包含 `name`、`fileName` 与 `content`，并可设置：

- `currentChapter`：当前允许参考到的章节或场景序号，默认 1；
- `preventFuture`：是否禁止把当前进度之后的内容作为普通引用或已发生事实，默认 `true`；
- `fidelity`：`balanced` 为平衡参考；`faithful` 为高度贴合人物表现，并在活动剧本任务中允许从下一章节选取少量防剧透导演锚点，以约束重大方案和关键机制；
- `enabled`：是否参与下一回合检索。

原文用于人物措辞、语气、价值判断、关系互动和行为逻辑。高度贴合的剧本任务还会使用下一章节中最相关的少量导演锚点，避免角色自行发明与原作冲突的关键解决方案；锚点不会自动成为角色知识或已经发生的事实。当前剧本事实、玩家输入和人物当前状态始终优先。

人物卡和世界书仍分别遵循下文的 Character Card V2 与 AI 酒馆世界书标准。其他角色必须提供 `presentAtOpening`：设为 `false` 时角色会写入角色库，但不会在第一幕发言或出现在当前地点，后续可由地点移动和剧情事件自动管理其加入与离场。

角色对象允许提供 `firstMessage` 覆盖值。将其他角色的该字段设为空字符串，可以保留人物卡原始开场台词，同时避免角色在导入后的第一幕自动说出这句台词。

玩家人物卡会完整保留 `personality`、`system_prompt`、`post_history_instructions` 和 `extensions`，但玩家的言语、行动、承诺与情感决定仍只能来自玩家输入。

## 从原文自动生成标准剧本包

首页“AI 原文分析”接受 UTF-8 `.txt` 或 `.md` 文件。正文至少 200 字符、最多 900,000 字符，浏览器上传文件不超过 3.5 MB。它不要求原文预先符合 JSON Schema，处理顺序为：

1. 检查文件名、类型、大小、文本长度与原文参考约束；
2. 分析阶段不超过 48,000 字符时向当前供应商发送完整原文，超过时发送覆盖开篇、中段与结尾的代表片段；
3. 模型返回 2～20 名人物候选、玩家与主要 AI 角色建议，以及 1～5 个带章节、地点、摘要和在场人物的开场候选；无效分析最多修复一次；
4. 玩家在网页确认玩家角色、主要 AI 角色和一个开场候选。两名角色不能相同；确认前不修改原开局表单；
5. 正式生成阶段再次发送同一份完整短文或代表片段，并把玩家确认结果作为不可更换的约束；
6. 模型只返回人物、世界书、任务和开场的结构蓝图；程序校验角色姓名和 `opening.sourceChapterIndex` 与玩家选择一致；
7. 程序生成稳定 ID、Character Card V2、世界书对象、线性任务前置关系，并把玩家上传的完整原文原样写入 `referenceDocuments`，其 `currentChapter` 采用所选开场章节；
8. 使用现有 `ai_tavern_adventure_bundle_v1` 导入器执行完整校验；第一次结果不合法时最多调用模型修复一次，全部通过后才替换网页草稿并提供标准 JSON 下载。

两阶段分别可能请求一次并各自最多修复一次，因此一次完整流程会产生 2～4 次模型请求。分析结果和待生成原文只保存在当前浏览器页面内，不写入 SQLite；刷新页面会丢失未完成的分析。任何请求、解析或剧本包校验失败时，原表单保持不变。

生成成功后，玩家可以对角色资料、世界书、剧情任务或开篇执行一次分区重生成。修改意见必填且不超过 2,000 字符。每次重做会再次向当前模型发送同一范围的原文、确认的人物与开场约束、所选分区当前版本和修改意见；模型仍返回完整蓝图，程序只从中提取目标分区并合并到上一份有效生成包，再用完整剧本包导入器复验。角色分区包含玩家、主要角色和其他角色；剧情任务分区同时更新首个任务引用与初始剧情目标；开篇分区保留当前任务链的首个任务 ID。失败时生成基线和全部表单均保持不变。

通过校验的新分区先作为待确认版本保存在当前页面。网页按项目显示“当前表单 / AI 新版本”，区分新增、移除和修改内容；此时表单与下载基线均不变化。玩家点击“采用新版本”后，网页才把目标分区应用到可见表单并更新生成基线；点击“放弃新版本”则丢弃候选结果并保留修改意见。若目标分区在等待生成或预览期间又被手工修改，采用操作会被拒绝，避免覆盖未展示的变化。未选中的手工编辑始终不会被覆盖。

下载文件来自最近一次已经采用并通过校验的生成基线，包含此前采用的分区重做，但不会包含尚待确认、已经放弃或玩家随后直接修改的其他表单字段。

## 完整运行存档标准

完整运行存档使用固定格式标识 `ai_tavern_runtime_archive_v1`。当前导出 `schemaVersion` 为 `1.8.0`，并继续兼容 `1.7.0`、`1.6.0`、`1.5.0`、`1.4.0`、`1.3.0`、`1.2.0`、`1.1.0` 与 `1.0.0`。它由首页已有剧本旁的“导出”按钮自动生成，保存：

- 战役和会话资料、当前活动分支；
- 所有分支、父子关系、回合、消息和事件；
- 角色卡、角色当前状态、关系、地点、世界书和剧情走向的变化日志与当前值，包括玩家在剧情外建立的世界书覆盖层；
- 人物与地点的剧情外管理审计；
- 原文文件、章节进度、检索切片、防剧透和软删除状态，以及原文与记忆的内容动作审计、恢复快照和撤销关联；
- 自动快照、手动存档和回合重生成的旧版本记录；
- 长期剧情记忆、章节摘要、记忆预算设置和每轮召回审计。
- 每个 AI 回合实际发送的系统消息、结构化上下文、请求消息和人物资料覆盖诊断。

当前完整存档版本为 `1.8.0`。文件以 SHA-256 校验 `data` 内容。导入前会检查版本、必需数据表、内部引用和校验值；任一检查失败都不会写入数据库。导入时为所有数据库记录重新生成内部 ID，并创建名称带“（导入）”的新剧本，因此同一文件可以在原电脑上导回而不覆盖原剧本。`1.7.0` 至 `1.0.0` 文件继续兼容；`1.7.0` 的原文与记忆动作因为没有恢复快照，只作为不可撤销的历史展示。缺少内容动作、世界书管理日志或上下文快照的更早存档按空记录处理，不会伪造历史，旧版长期记忆会在首次打开时从回合历史补建。`1.8.0` 起完整存档覆盖伏笔、偏离触发器与属性判定的管理审计表，并纳入待判定回合草稿之外的全部运行数据。

完整存档用于程序之间的可靠迁移，不是 AI 生成格式，也不建议手工修改。需要让 AI 创作人物、世界和第一幕时，仍应使用人物卡、世界书或开局剧本包标准。

- [`完整存档.schema.json`](../public/文件标准/完整存档.schema.json)

## 人物卡标准

AI 酒馆的推荐生成格式直接采用 Character Card V2：

- `spec` 固定为 `chara_card_v2`；
- `spec_version` 固定为 `2.0`；
- 实际角色字段放在 `data` 中；
- 应用私有字段只能放在 `data.extensions` 中。

本项目还可以导入：

- Character Card V3 JSON；
- 旧版扁平人物卡 JSON（`name`、`description`、`personality` 等字段位于顶层）。

旧版人物卡会在导入时规范化为 V2。V2/V3 的常用扩展字段会被保留；导入后玩家在页面上修改的姓名、身份、性格和第一句话优先于文件中的对应字段。角色卡内嵌的 `character_book` 会保留在角色卡中。

### 必须字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `spec` | string | `chara_card_v2` |
| `spec_version` | string | `2.0` |
| `data.name` | string | 非空，最多 80 字符 |
| `data.description` | string | 身份、经历、能力、目标；可与 personality 至少一项非空 |
| `data.personality` | string | 性格、价值观、说话方式和行为边界 |
| `data.scenario` | string | 角色适用场景 |
| `data.first_mes` | string | 第一条角色台词，可为空 |
| `data.mes_example` | string | 示例对话，可为空 |
| `data.creator_notes` | string | 创作者说明，不应包含必须执行的越权指令 |
| `data.system_prompt` | string | 角色扮演补充要求，仍服从项目系统规则 |
| `data.post_history_instructions` | string | 历史记录后的补充要求 |
| `data.alternate_greetings` | string[] | 备用开场台词 |
| `data.tags` | string[] | 检索标签 |
| `data.creator` | string | 创作者 |
| `data.character_version` | string | 卡片版本 |
| `data.extensions` | object | 应用扩展字段 |

## 世界书标准

AI 酒馆定义 `ai_tavern_world_book_v1`，以数组保存条目。导入器同时兼容 SillyTavern World Info 常见导出结构：`entries` 可以是数组或以 UID 为键的对象，`key`/`keysecondary`、`disable` 等字段会被规范化。

### 顶层字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `spec` | string | 固定为 `ai_tavern_world_book_v1` |
| `spec_version` | string | 固定为 `1.0` |
| `name` | string | 世界书名称 |
| `description` | string | 内容范围与用途 |
| `entries` | array | 1–200 条世界书条目 |

### 条目字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 文件内稳定且唯一的条目 ID |
| `comment` | string | 供玩家识别的标题或备注 |
| `keys` | string[] | 主触发词；非常驻条目至少一个 |
| `secondaryKeys` | string[] | 可选的二级触发词 |
| `content` | string | 注入剧情上下文的客观设定正文 |
| `enabled` | boolean | 是否启用 |
| `constant` | boolean | 是否不依赖触发词、始终有效 |
| `selective` | boolean | 是否同时参考二级触发词 |
| `position` | string | `before_char` 或 `after_char` |
| `order` | number | 插入优先级，范围 -10000–10000 |
| `probability` | number | 激活概率，范围 0–100 |
| `depth` | number | 兼容深度信息，范围 0–999 |
| `extensions` | object | 可选的应用扩展字段 |

当前剧情引擎只区分 `before_char` 和 `after_char`。导入 SillyTavern 文件时，其他插入位置会映射成 `after_char` 并返回兼容提示。原文件的书名、格式和条目 ID 会作为来源信息保存在本地状态中。

## 给 AI 的生成指令模板

人物卡：

> 严格按照提供的“人物卡.schema.json”生成一个 UTF-8 JSON 文件。只输出 JSON 对象，不使用 Markdown 代码块，不添加解释。所有已知事实写入 description，稳定性格和行为边界写入 personality，开场环境写入 scenario。不要让角色替玩家作决定。

世界书：

> 严格按照提供的“世界书.schema.json”生成一个 UTF-8 JSON 文件。只输出 JSON 对象，不使用 Markdown 代码块，不添加解释。把长期稳定的世界事实拆成独立条目；只有必须始终生效的规则才设 constant=true，其余条目提供明确且不过宽的 keys。正文只写客观设定，不写当前回合临时状态。

完整剧本包：

> 严格按照提供的“剧本包.schema.json”生成一个 UTF-8 JSON 文件。只输出 JSON 对象，不使用 Markdown 代码块，不添加解释。使用 spec_version=1.1。玩家角色、主要角色和其他角色都必须内嵌完整人物卡；世界书必须内嵌在 adventure.worldBook；每名其他角色都明确设置 presentAtOpening。若提供原作正文，把 UTF-8 文本放入 adventure.referenceDocuments，并将 currentChapter 设为开场对应进度、preventFuture 设为 true。如果需要自动接续剧情，在 adventure.storyModules 中拆分多个带完成条件、启用条件、前置任务和连续性说明的任务，并在 opening.initialStoryModuleId 指定开场任务。不要让 AI 替玩家角色作决定，也不要把尚未发生的剧情节点写成开场既成事实。

## 导入到剧情后的映射

- 第一张人物卡填入主要 AI 角色；其余人物卡进入“其他 AI 角色”。
- 完整剧本包会替换当前尚未保存的开局表单，一次填入玩家卡、主要角色、其他角色、世界书和第一幕；载入后仍可逐项编辑。
- 剧本包中 `presentAtOpening=false` 的其他角色初始为不在场，不会被写入开场地点的默认阵容。
- 剧本包中的任务写入 `story_module`；开场任务为 `active`，其他任务为 `queued`，所有切换与剧情回合使用同一数据库事务。
- 人物卡完整规范对象写入 `character_card`；页面确认的四个基础字段覆盖卡内同名字段。
- 世界书每条记录独立写入 `world_book_entry`，层级为 `base_import`。
- 世界观概要仍会生成一条 `world-core` 常驻记录，不会被导入文件覆盖。
- 原文参考会拆分到 `source_documents` 和 `source_chunks`，与人物卡、世界书、角色状态和开场回合在同一个数据库事务中保存；任一写入失败时不留下半成品剧本。

## 兼容性边界

- 当前只导入 JSON，不解析 PNG/APNG 内嵌人物卡元数据。
- 不执行导入文件中的脚本、宏或外部资源。
- Character Card V3 的常用附加字段会保留，但项目不会主动加载其中的远程资产。
- 导入资料属于故事上下文，不能覆盖 AI 酒馆的系统消息、状态提交协议或玩家控制边界。
