# GitHub 公开发布指南

## 当前仓库为什么不能直接推送现有 main 历史

本地数据库、备份、`.env.local` 和桌面发布包一直由 `.gitignore` 排除，当前跟踪树中没有这些文件。但私有开发历史曾提交过本机专用的长文本测试资料。只在最新提交删除文件不能清除旧提交，因此不得把现有私有 `main` 历史直接推送到 GitHub。

推荐保留本地 `main` 作为私有开发档案，另建一个没有父提交的 `github-main` 根提交。公开分支只包含审计后的当前源码，不继承私有测试历史。

## 首次发布流程

1. 确认工作区变更已经提交，并运行 `npm run public:check`。
2. 从当前安全文件树建立无父提交的 `github-main` 分支。
3. 运行 `npm run public:check:history -- --ref=github-main`，结果必须通过。
4. 在 GitHub 创建一个空仓库，不要让网站自动生成 README、许可证或 `.gitignore`。
5. 只把本地 `github-main` 推送为远端 `main`，不要使用 `git push --all`、`git push --mirror` 或推送本地私有 `main`。
6. 推送后在 GitHub 网页重新检查仓库文件列表、提交历史、Actions 日志和 Release 附件。

公开源码采用根目录 [`LICENSE`](../LICENSE) 中的 MIT License，项目元数据、README 和许可证文件应始终保持一致。

远端地址尚未确定，因此本项目不会自动创建 `origin` 或执行任何网络推送。

## 必须保持为本地文件的内容

- `.env.local` 与桌面版 `用户数据/配置/模型.env`；
- `data/`、`用户数据/`、SQLite、WAL/SHM 和数据库备份；
- 单剧本完整存档、玩家主动导出的 JSON 和日志；
- `测试资料/` 中的私有原文、人物卡、世界书和剧本包；
- `发布/`、`桌面构建/`、DMG、ZIP 和未审计的应用包。

## 后续更新

每次准备公开更新时，先在私有开发分支完成测试，再把经过审计的源码变更整理到 `github-main`。公开分支上的每个提交都应通过 `npm run public:check`；准备 Release 时仍要单独运行桌面包自带的敏感信息验证。

如果真实密钥曾经进入任何提交，不能依赖本指南中的“新公开分支”代替密钥吊销。应先在供应商处撤销密钥，再检查所有可能的远端副本。
