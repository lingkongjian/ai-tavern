# AI 酒馆：产品范围与架构草案

具体的模型输入输出、角色卡演化、角色当前状态和世界书同步规则见 [`GENERATION_SPEC.md`](GENERATION_SPEC.md)。

## 已确认的产品决策

- 模型调用采用可扩展供应商层；默认兼容现有 DeepSeek 配置，提供 OpenCode Go 预设，并支持自定义 OpenAI Chat Completions 兼容云端或本地服务。
- 模型设置可以读取标准 `/models` 目录、导出不含密钥的模型清单，并通过配置、目录、协议和最小 JSON 生成四类检查审核所选模型；目录可见不能代替实际 token 权限审核。
- 模型调用只走本地服务端，剧情编排层不依赖具体供应商或模型名。
- 候选选项必须根据当前场景的提问类型动态生成，不能每轮机械地套用同一组立场。
- 界面提供三种语义不同的玩家输入框。
- 角色卡兼容 Tavern Character Card V2；世界书兼容 SillyTavern World Info/Lorebook 的常见 JSON 导入导出格式。
- 提供网页生成向导及内部生成 API，用自然语言快速生成角色卡和世界书。
- 开局页面支持批量导入 JSON 人物卡和世界书，导入前先完成格式校验与规范化。
- 开发阶段在 macOS 上提供双击启动器；正式版本封装为不显示终端的本地 `AI酒馆.app`。

## 核心回合

一局游戏由世界设定、AI 扮演角色、玩家角色和连续回合构成。每一回合中，系统应：

1. 结合世界规则、角色档案、当前场景、人物关系和关键历史生成剧情。
2. 让 AI 角色以符合自身目标、知识边界和行为约束的方式作出反应。
3. 判断当前是在回应对方的提议，还是在决定玩家下一步怎么做。
4. 按判断结果生成相应候选选项，同时始终保留玩家自定义入口。
5. 合并玩家的选项、角色言行和剧情走向意图，生成当前回合结果。
6. 判断本轮是否产生了会影响未来剧情的持久世界事实，并生成对应世界书变更。
7. 提交回合结束时的当前位置与完整在场阵容，自动处理人物加入、离场和随场景移动。
8. 把剧情结果、场景状态、走向状态和世界书变更作为同一次结构化状态提交保存，再进入下一回合。

## 动态候选选项

### 回应提议

当 NPC 提出交易、请求、威胁、条件或合作建议时，候选项围绕以下语义生成：

- `accept`：接受核心提议。
- `partial_accept`：只接受一部分、附加条件、协商或拖延决定。
- `reject`：明确拒绝，也可根据角色性格生成温和或强硬表达。
- `custom`：玩家自行输入不受上述分类限制的回应。

### 决定行动

当剧情询问玩家接下来如何行动时，候选项覆盖具有明显差异的立场：

- `benevolent`：善意、保护、合作、克制或牺牲性的行动。
- `neutral`：务实、观察、回避、交换或风险平衡的行动。
- `malicious`：欺骗、操纵、伤害、背叛或利用局势的行动。
- `custom`：玩家自行输入其他行动。

善恶标签只用于帮助玩家理解选项差异，不应强行改变玩家角色的既有性格，也不应让所有回合固定生成相同数量的选项。

## 三种玩家输入

1. **自定义选项输入**：当玩家选择 `custom` 时出现，用来替代 AI 给出的候选选项；它属于当前决策本身。
2. **角色言行输入**：供玩家直接写出角色在当前场景中说的话、做的动作，或二者的组合；它属于故事内信息。
3. **剧情走向输入**：供玩家表达希望后续出现或避免的情节、节奏和发展方向；它属于故事外的导演意图，默认不应被 NPC 当作已知事实。

剧情走向输入应作为会话级软约束保存，并持续影响后续回合。它在以下任一条件满足时结束：

- 玩家输入新的剧情走向，旧走向被替换。
- 玩家主动清空或取消当前剧情走向。
- 后续生成的剧情已经实际完成当前走向所描述的目标。

系统应在每轮结束后评估当前走向是否已经完成，并记录来自已发生剧情或状态变化的完成依据。不能只因为模型声称“已完成”就停止；完成判断必须能够指向本轮或此前回合中已经发生的事件。完成后不再把该走向注入后续提示词，但应保留在历史记录中，并允许玩家重新启用或改写。

剧情走向不能覆盖世界硬规则、角色知识边界和必要的安全限制。

## 角色卡和世界书兼容

### 角色卡

第一版以 Tavern Character Card V2 为兼容基线：

- 支持 V2 JSON 导入与导出。
- 数据外层使用 `spec: "chara_card_v2"`、`spec_version: "2.0"` 和 `data`。
- 覆盖名称、描述、性格、场景、首条消息、示例对话、系统提示、历史后指令、备选开场、标签和内嵌角色世界书等常用字段。
- 导入后保留未知 `extensions` 字段，重新导出时不能静默丢失第三方扩展数据。
- PNG 嵌入式角色卡作为同一 V2 数据模型的文件适配器规划，JSON 先行。

### 世界书

第一版支持 SillyTavern 常见 World Info/Lorebook JSON：

- 条目包含触发关键词、正文、启用状态、常驻策略、插入位置、顺序和扩展字段。
- 导入时转换为项目内部统一结构，导出时恢复兼容格式。
- 关键词触发只是提示词检索机制，不保证模型一定在回复中提到对应设定。
- 角色卡内嵌的 `character_book` 与独立世界书可以同时生效，角色专属条目优先。

### 剧情与世界书同步

部分剧情走向会改变世界中的持久事实，例如地点被毁、统治者更替、阵营关系改变、新规则生效或重要人物死亡。此类变化必须同步到世界书，否则后续检索可能重新注入已经过时的设定。

- 每轮结束后，从已经实际发生的剧情和结构化状态变化中提取世界书变更。
- 支持 `create`、`update` 和 `deactivate`，默认不物理删除旧条目，以便追踪历史。
- 每项变更记录来源回合、关联剧情走向和修改原因。
- 只有会影响未来场景理解的持久事实进入世界书；临时动作、普通对话和短期情绪保留在回合或关系状态中。
- 剧情结果、剧情走向完成状态和世界书同步必须原子提交，任一步校验失败都不能只保存其中一部分。
- 游戏过程中自动写入当前会话的动态世界书层，并立即参与后续检索。
- 玩家导入的基础世界书保持原样；工作台编辑会建立玩家修订覆盖层，并按字段展示与基础层的差异。玩家可软删除、重新启用或撤销覆盖层以恢复基础版本。
- 若新剧情推翻旧事实，优先停用或更新旧条目，避免相互矛盾的条目同时触发。

## 快速生成接口

网页端提供两个生成向导：

- **生成角色卡**：输入人物概念、性格、背景、与玩家关系、说话风格、禁忌和开场场景，预览并编辑后导出 V2 JSON。
- **生成世界书**：输入题材、时代、地区、阵营、规则、重要人物和禁忌，生成可编辑的触发词条，再导出兼容 JSON。

内部接口暂定为：

- `POST /api/generate/character-card`
- `POST /api/generate/world-book`

接口返回结构化 JSON、校验结果和警告；生成内容在保存或导出前必须允许玩家审阅和修改。

## 建议的系统分层

- **界面层**：展示场景、候选选项、三种输入、生成向导和导入导出界面。
- **剧情编排层**：识别决策类型、组装上下文、控制回合、校验模型输出并处理失败重试。
- **角色决策层**：根据角色身份、秘密、关系、目标与道德倾向生成行为。
- **模型适配层**：统一封装 Chat Completions、鉴权、JSON 输出差异和供应商错误；供应商专属参数不得进入剧情业务逻辑。
- **兼容层**：解析、校验并导入导出 Tavern Card 与 World Info 格式。
- **状态层**：保存世界、角色、会话、回合、关系值、事件标记、动态世界书和剧情摘要。

## 第一版数据对象

- `World`：世界规则、地点、阵营、禁忌与背景资料。
- `Character`：身份、性格、目标、秘密、知识边界和行为约束。
- `Session`：玩家角色、当前场景、带生命周期的剧情走向目标和剧情摘要。
- `Turn`：场景输入、决策类型、候选反应、三种玩家输入和状态变化。
- `Relationship`：角色之间的信任、恐惧、好感、敌意等可变关系。
- `Location`：地点资料、默认登场人物、最近到访回合和启用状态。
- `WorldBookChange`：由剧情产生的世界书新增、更新或停用操作及其来源证据。

## API 与安全边界

- 模型 API Key 只允许在服务端读取；浏览器只能获知是否已经保存密钥。
- 浏览器只调用本项目自己的服务端接口，不直接请求外部模型供应商。
- 模型输出采用 JSON 模式并经过运行时校验，不能直接信任。
- 世界观资料与最近回合不无限累积；当前采用最近回合、章节摘要、关键词召回的长期记忆和状态相关性筛选组成分层上下文，并受可配置 token 预算约束。
- 对模型超时、限流、空内容、格式错误和断线提供明确恢复路径。
- 模型生成的角色卡和世界书始终先进入草稿态，未经玩家确认不自动覆盖已有内容。
- 动态世界书可在当前会话中自动更新，但永久合并到玩家的基础世界书前必须确认差异。

## 当前实施取舍

- 游戏记录从第一版开始保存在本机 SQLite，不把浏览器存储作为正式剧情来源。
- 开局向导可以建立一名玩家角色、主要 AI 角色和多名其他 AI 角色；游戏中的统一剧本工作台继续管理人物、地点、剧情任务、世界书、原文、记忆和修改记录，新的剧本内容编辑能力不得再建立孤立入口。
- 开局向导允许玩家上传 TXT/Markdown 原文：先调用当前模型分析人物与开场候选，玩家确认玩家角色、主要 AI 角色和开场章节后，再生成标准剧本包草稿。程序必须拒绝擅自更换确认结果的输出，并负责规范组装、完整原文内嵌和正式导入校验；分析阶段不改表，生成成功后才自动填入，任一失败不得覆盖旧表单或写入数据库。
- 已生成的开局草稿支持凭必填修改意见单独重做角色资料、世界书、剧情任务或开篇。服务端必须只合并目标分区并复验完整剧本包；网页先展示当前值与新值差异，只有玩家明确采用且预览基线未变化时才更新目标字段。放弃、冲突和失败不得改变表单、下载基线、非目标编辑或原文参考。
- 工作台中的人物、地点、剧情任务、世界书、原文和记忆统一使用版本化内容命令、错误格式和刷新快照；修改记录统一读取资料和状态审计，跨领域状态回滚与字段锁保留专用接口，详见 [`CONTENT_SERVICE.md`](CONTENT_SERVICE.md)。
- 工作台的人物栏目可以新增、编辑、离场或启停 AI 角色；地点栏目可以新增、编辑、移动或启停地点，并配置手工移动时的默认登场人物。所有人物使用独立角色 ID、角色卡、当前状态和关系状态，剧情回合通过结构化场景变化自动同步地点和最终出场阵容。
- 玩家可以对当前最新的 AI 回合执行重生成；系统从父回合状态重新推演、原子替换最新结果并保留旧版本，不能把重生成错误实现为额外推进一回合。

玩家提供文件、SQLite 内部记录和模型 API 请求内容必须经过同一套解析、规范化、校验、保存与预算选择边界，详见 [`FILE_LIFECYCLE.md`](FILE_LIFECYCLE.md)。
