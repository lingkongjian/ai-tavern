# 模型供应商接入与回合生成

AI 酒馆通过本地服务端调用玩家选择的模型供应商，浏览器不会直接获得或发送 API Key。文件名为历史兼容路径；本文现为多供应商接入的权威说明。

## 配置

首页左下角“模型设置”支持以下预设：

- `deepseek`：兼容既有 DeepSeek 环境变量，并发送 DeepSeek 专用的关闭思考参数；
- `opencode_go`：预填 OpenCode Go 地址，自动读取套餐模型目录，并区分当前酒馆可调用的 Chat Completions 模型与尚未适配的其他协议模型；
- `openai_compatible`：自定义 OpenAI Chat Completions 兼容云端接口，需要 API Key；
- `local_openai_compatible`：本机兼容接口，允许不填写 API Key。

推荐在网页中填写，先读取模型并执行可用性审核；保存会以 `0600` 权限写入项目根目录 `.env.local`，同时更新当前开发进程，无需重启。设置页顶部显示当前 API 的名称、类型、模型、鉴权和地址；删除配置时只移除 `AI_PROVIDER`、`AI_API_BASE_URL`、`AI_API_KEY`、`AI_MODEL`、`AI_JSON_MODE`，保留文件中的其他变量和全部游戏数据。也可以手工配置：

```dotenv
AI_PROVIDER=deepseek
AI_API_BASE_URL=https://api.deepseek.com
AI_API_KEY=你的密钥
AI_MODEL=deepseek-v4-flash
AI_JSON_MODE=response_format
```

旧配置缺少 `AI_PROVIDER` 时继续按 DeepSeek 处理。手工修改后需要重新启动程序。设置接口只返回“是否存在密钥”，不会返回密钥正文。

同一供应商下留空密钥会沿用本机已有值；切换供应商时不会复用旧密钥，云端服务必须重新填写，本地无鉴权服务则保存为空。这条规则避免把一家供应商的密钥误发给另一地址。

## 模型目录与可用性审核

“读取模型”根据 Base URL 请求标准 `/models` 端点。Base URL 若已经是 `/chat/completions`、`/messages` 或 `/responses`，程序会替换末尾协议路径；否则直接追加 `/models`。返回的 `data`、`models` 或顶层数组会规范化为统一目录，最多读取 5000 项，并按以下状态分类：

- `chat_completions`：目录元数据或已核对的供应商文档表明当前酒馆协议可用；
- `unknown`：目录没有协议元数据，允许选择，但必须实际审核；
- `unsupported_protocol`：使用 Messages 或 Responses 等尚未接入的协议，界面显示但禁止选择。

“审核可用性”依次检查配置与 HTTPS 边界、模型目录、所选模型协议，再用所选模型发起一次最多 64 token 的最小 JSON 生成。只有实际生成成功且返回预期 JSON 才算通过。读取目录通常不产生生成 token，但目录公开可见或包含某个模型，不代表当前套餐 token 拥有生成权限。已知协议不兼容时会跳过生成，避免无效请求；供应商没有 `/models` 时目录检查为警告，仍以最小生成结果为准。

OpenCode Go 的官方目录为 `https://opencode.ai/zen/go/v1/models`。其套餐同时暴露 Chat Completions、Messages 和 Responses 模型，而当前酒馆只实现 Chat Completions；官方模型列表变化后，新 ID 会先标记为“需要审核”，不会因本地旧名单而被直接拒绝。依据见 [OpenCode Go 官方文档](https://dev.opencode.ai/docs/go/)。

目录可以导出为 UTF-8 JSON，格式为 `schemaVersion=1.0.0`、`kind=ai_tavern_model_catalog_v1`。文件包含供应商、Base URL、读取时间、兼容性分类、所选模型及本次审核结果，不包含 API Key。`verifiedModel` 只有在当前所选模型完成审核时才有值；该文件用于诊断和迁移选择，不会被导入为运行配置，也不能代替日后的重新审核。

## 请求方式

[`lib/ai/模型供应商.ts`](../lib/ai/模型供应商.ts) 统一调用兼容 OpenAI 格式的 `/chat/completions`；[`lib/ai/深度求索.ts`](../lib/ai/深度求索.ts) 仅保留旧代码导入兼容：

- `AI_JSON_MODE=response_format` 时发送 `response_format: { "type": "json_object" }`；若供应商不支持该字段，可改为 `prompt_only`，仅依靠系统提示要求 JSON。
- 只有 DeepSeek 预设发送 `thinking: { "type": "disabled" }`；通用兼容服务不会收到供应商专属字段。
- 默认最长等待 90 秒。
- 不使用流式输出；完整结果校验通过后一次显示。
- 远程接口必须使用 HTTPS；只允许本机兼容服务使用 HTTP。
- Base URL 可以停在版本路径，也可以直接包含 `/chat/completions`，适配器不会重复追加。

系统提示会告诉当前模型供应商：本游戏中的世界、事件和角色均为虚构；对于资料中明确为成年、且双方当前自愿的角色，原作中的亲密情节可以继续作为人物表达和关系发展的参考，不应仅因内容亲密而自动回避、说教、强制淡出或跳过。该规则不会放宽玩家控制权：模型不能替玩家同意或完成玩家没有输入的亲密行为，婚约、既往关系与原作剧情也不等于当前同意；成年身份不明确、拒绝、撤回同意或无法同意时不得升级亲密内容。外部供应商自身的服务规则仍可能对最终输出生效。

## 原文生成剧本包

原文分析与剧本包生成使用创建前接口，不是剧情回合：

1. `POST /api/imports/analyze-source` 接受一份 UTF-8 TXT/Markdown 原文，校验文件名、200 至 900,000 字符限制和原文参考格式；
2. 分析阶段短文完整发送，长文按章节选择开篇、全书分布与结尾片段，总计最多 48,000 字符；当前供应商返回人物、推荐分工和开场候选，单次输出预算最多 6,000 token；
3. 玩家在浏览器确认玩家角色、主要 AI 角色和开场候选。分析结果与完整原文暂存在当前页面，不写入数据库；
4. `POST /api/imports/generate-bundle` 再次发送相同范围的原文，并把确认结果作为硬约束；当前供应商返回不含内部 ID 的结构蓝图，单次输出预算最多 12,000 token；
5. 本地程序校验人物姓名、`opening.sourceChapterIndex` 和确认结果一致，再组装 Character Card V2、世界书、线性任务链和完整原文参考，并调用标准剧本包解析器校验；
6. 每个阶段首次结构不合法时只携带上一版 JSON 和校验问题修复一次；再次失败则返回错误，不改变网页表单；
7. 成功结果只作为浏览器中的可编辑开局草稿，并分别返回模型、请求次数和 token 用量，不写入剧情数据库。两个阶段最长等待均为 180 秒。

生成成功后，`POST /api/imports/regenerate-bundle-section` 可以重做 `characters`、`world_book`、`story_modules` 或 `opening`。请求携带最近一次有效生成包、目标分区和必填修改意见；服务端从内嵌原文恢复确认约束，再调用当前供应商生成完整候选包，只合并目标分区并复验整包。每次分区重做都是新的模型调用，可能因首次输出无效再修复一次；它不读取或写入 SQLite。网页收到结果后先建立当前表单与新版本的项目级差异，不立即更新任何字段；只有玩家点击采用且目标分区快照仍与请求前一致时，才更新目标表单和生成基线。放弃或快照冲突不会再次调用模型。

原文中的提示词、日志和指令都被标记为不可信待分析文本，不能覆盖系统消息。玩家确认结果也只能选择人物分工和开场，不能覆盖系统安全边界或标准包协议。模型负责抽取结构，不负责复述完整原文；程序把玩家上传的正文直接内嵌到标准包，并把所选开场章节写入原文进度，因此长文未发送部分仍会在创建剧本后成为本地原文参考。

## 单回合流程

`POST /api/adventures/:sessionId/turns` 按以下顺序工作：

1. 校验候选选择、自定义选项、角色言行和剧情走向。
2. 检查客户端提交的分支头，过期输入不会调用模型。
3. 读取当前有效世界书、基础角色卡、角色演化、角色状态、关系、地点和最近回合。
4. 生成本轮专用 ID，并要求所有角色卡与世界书变化引用该 ID。
5. 通过当前供应商适配器请求结构化 JSON。
6. 校验事件、对话、候选项、角色 ID、地点 ID、最终在场阵容、世界书 ID、变化路径和证据引用。
7. 第一次结构校验失败时，携带错误列表要求当前模型修复一次。
8. 把剧情、消息、事件、地点与出场变化、角色状态、关系、角色演化、动态世界书、剧情走向和本轮实际上下文快照作为一个事务保存。
9. 返回重新加载后的完整会话状态，网页显示新回合、本轮实际状态变化和 token 用量。

模型请求失败或两次输出都不合法时，第 8 步不会执行。

## 最新回合重生成

游戏页只允许重新生成当前分支最新的 AI 回合。玩家必须先填写不满意的原因或具体修改意见，服务端会把经过长度和空值校验的意见放入独立标记区，并明确它不能覆盖系统规则、既定世界观、角色卡、父回合状态或输出协议。系统沿用该回合原来的候选选择、自定义选项、角色言行和剧情走向，从其父回合结束时的状态重新组装提示词；不会把玩家不满意的旧版剧情当作已经发生的事实。重生成会再次产生当前供应商的正常 token 用量。

分支起点如果继承自父分支，不能在子分支中直接替换；玩家可以切回拥有该回合的原分支重新生成，或从更早回合建立另一分支。子分支产生自己的第一个 AI 回合后，后续生成与重生成都只使用冻结的分支起点和该分支自己的变化，父分支的新剧情不会进入提示词。

新输出通过校验后才会原子替换最新回合的叙述、对话、事件和状态变化。旧版结构化输出保存在本地重生成记录中。相同请求标识的重试直接返回已经替换的回合；失败、冲突或手工人物/地点修改保护触发时，现有剧情保持原样。

## 世界书和角色卡边界

- 基础角色卡不会被模型直接修改；长期剧情变化写入 `character_card_evolution`。玩家在人物管理中确认的编辑可以直接更新本地基础卡。
- 模型更新基础世界书时，系统会创建会话动态覆盖层，而不是覆盖玩家原始条目。
- `base_import` 与内置 `base` 使用同一保护规则；玩家在工作台建立的 `player_override` 优先于两种基础层。
- 停用的玩家覆盖层仍作为遮罩存在，基础旧事实不会因此重新进入请求；只有玩家明确恢复基础版本才撤销遮罩。
- 被动态层覆盖的基础条目不会重复注入后续提示词。
- 剧情走向只有在模型引用实际事件或对话作为完成证据时才能自动结束。
- 暂时离场角色保留角色卡，但 `present=false`；模型只有在本轮明确描写其回归，并把角色写入 `sceneTransition.presentCharacterIds` 时才能让其重新参与。
- 停用角色不会出现在可用角色 ID 中，模型不能继续扮演或引用该角色。
- 每轮 `sceneTransition` 提交回合结束时的当前位置和完整在场阵容。后端自动计算人物加入与离场，普通角色状态补丁不能另行修改 `present` 或 `locationId`。
- 进入未知地点会建立会话地点资料；进入已有地点必须沿用其 ID，停用地点不能被模型重新进入。

## 重复提交

网页为每次玩家提交生成幂等键。网络中断后使用同一个键重试时，系统会直接返回已经保存的回合，不会再次调用模型，也不会重复写入或重复计费。

## 用量记录

- 供应商返回的输入、输出和合计 token 会随本轮叙述消息写入本地数据库。
- 网页的“本轮变化”面板会显示生成模型和三类 token 数值；供应商未返回某项用量时显示为 `—`。
- 如果第一次结构校验失败并触发一次修复请求，系统会把两次请求的 token 相加，展示该回合的实际总消耗。
- 手工开局和普通 JSON 导入不调用模型，因此第一回合不会产生模型 token；原文分析与正式生成是创建前的两阶段独立调用，其用量不计入第一回合。

## 实际上下文与人物依据诊断

每次 AI 生成会把发送时的系统消息、结构化故事上下文、最终请求消息、本地 token 估算、供应商输入 token、请求次数和是否触发结构修复写入 `turn_context_snapshots`。该快照与回合 ID 一一对应；重生成成功时以新请求原子替换，失败时保留原快照。游戏页只在玩家打开查看器时按回合加载完整内容，常规剧情页面不会重复传输大型提示词。

诊断是可验证的输入覆盖检查：逐个列出人物的基础角色卡、当前状态、原文片段和长期记忆是否进入本轮请求，并报告状态预算省略数与各上下文分区的本地估算。它用于解释人物表现偏差可能缺少哪类依据，不对模型输出做不可验证的“还原度百分比”评分。

## 当前限制

- 还没有流式逐字显示。
- 当前生成协议只覆盖 OpenAI Chat Completions；Messages 与 Responses 模型会在目录中标为暂不支持。
- 可用性审核只实际调用当前所选模型，不会自动逐个调用整个目录，避免批量扣费和触发速率限制。
- 目前只显示供应商返回的 token 数量，还没有按实时单价估算金额。
- 本地完整运行存档已经支持导出和导入；跨设备自动同步不在单机版本范围内。
