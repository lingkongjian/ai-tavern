# 本地存储设计

AI 酒馆以本机 SQLite 作为正式数据源，不使用线上数据库或浏览器存储保存正式剧情。

## 数据位置

默认数据库文件：

```text
data/ai-tavern.sqlite
```

可以通过 `.env.local` 中的 `AI_TAVERN_DATA_DIR` 修改整个本地数据目录。相对路径以项目根目录为基准。

macOS 桌面版由桌面入口强制设置绝对数据目录：`AI酒馆/用户数据/数据/ai-tavern.sqlite`。备份位于其 `backups/` 子目录；模型配置、Electron 缓存和日志也分别保存在外层 `用户数据/` 的对应子目录。桌面版不会复用源码开发目录的 `data/` 或 `.env.local`。应用和 `用户数据` 必须一起放在可写的外层 `AI酒馆` 文件夹中，删除整个文件夹即可清除程序主动建立的本机持久数据。

`data/` 已排除在 Git 追踪范围之外，玩家剧情、导入内容和数据库不会进入源码提交。

整库备份默认位于 `data/backups/`。系统在已有数据库启动、数据库迁移完成和正常进程退出时自动建立 SQLite 一致性备份；首页也可立即手动备份。默认保留最近 12 份，可通过 `AI_TAVERN_BACKUP_RETENTION` 调整为 3–50 份。

## 数据结构

- `campaigns`：一个世界或游戏项目。
- `sessions`：一次连续剧情会话，并记录玩家当前选中的活动分支。
- `branches`：主线和后续剧情分支，保存当前头回合。
- `turns`：只追加的回合记录，保存玩家输入和模型结构化输出。
- `messages`：当前回合中的玩家、角色和叙述消息。
- `events`：模型输出中已经实际发生的结构化剧情事件。
- `state_changes`：角色状态、角色卡演化、世界书、关系和剧情走向的变化日志。
- `character_management_changes`：玩家在剧情外新增、编辑、离场或启停人物的独立审计日志。
- `location_management_changes`：玩家在剧情外新增、编辑、移动或启停地点的独立审计日志。
- `story_module_management_changes`：玩家在剧情外新增、编辑或启停预埋任务的独立审计日志。
- `world_book_management_changes`：玩家在剧情外新增、编辑、启停、软删除或恢复世界书覆盖层的独立审计日志。
- `content_asset_management_changes`：玩家导入、调整或删除原文，以及修正、配置、重建或撤销记忆时的统一动作审计；保存请求哈希、同对象修订序号、恢复前后快照和撤销关联。原文快照不复制正文，记忆快照只保存恢复必需字段。
- `state_control_changes`：玩家撤销历史状态变化时追加的补偿式状态日志。
- `state_field_lock_changes`：剧本级字段锁定与解除记录，作用于该剧本的全部分支。
- `state_lock_blocks`：每回合被字段锁拦截的 AI 状态修改及原始建议。
- `turn_regenerations`：最新 AI 回合的重生成记录，保存替换前与替换后的结构化剧情。
- `source_documents`：剧本导入的本地原文、原作进度、防剧透、贴合度和软删除状态。
- `source_chunks`：从原文按章节与场景切分的检索片段及人物标签。
- `materialized_states`：从变化日志计算出的当前有效状态，用于快速恢复游戏。
- `snapshots`：开局、每五回合及分支起点的不可变阶段快照。
- `save_points`：玩家命名的手动存档，保存当时完整物化状态，可"恢复为新分支"或直接恢复（见"恢复到恢复点"）。

版本化 SQL 位于 [`drizzle/`](../drizzle/)，由 [`db/schema.ts`](../db/schema.ts) 生成。

## 单回合原子提交

[`LocalStoryStore.commitTurn()`](../lib/storage/story-store.ts) 在一个 `BEGIN IMMEDIATE` 事务中完成：

1. 检查会话、分支和预期头回合。
2. 写入本轮玩家输入与模型输出。
3. 写入消息和事件。
4. 追加所有状态变化日志。
5. 更新当前物化状态。
6. 更新分支头和下一回合序号。

任一步失败都会回滚整个回合，避免出现“剧情已保存，但角色卡或世界书没有同步”的情况。

## 原子化创建第一局

[`LocalStoryStore.startAdventure()`](../lib/storage/story-store.ts) 同样使用一个事务，同时建立：

1. 战役、会话与主线分支。
2. 玩家角色、主要 AI 角色和其他 AI 角色的基础 Character Card V2 数据。
3. 所有角色的初始当前状态与关系状态。
4. 开场地点、当前位置和默认登场阵容。
5. 基础世界书核心条目。
6. 导入人物卡的完整规范字段和导入世界书的独立基础条目。
7. 可选的初始剧情走向。
8. 可选的 `story_module` 剧情任务链及开场任务状态，以及可选的 `plot_thread` 伏笔（foreshadowing）与 `plot_trigger` 偏离触发器（triggers）实体。
9. 可选原文参考及其章节检索片段。
10. 开场事件、叙述、角色台词和第一组行动候选项。

因此开局中途发生错误时，不会留下只有战役名称、却没有角色卡或世界书的不完整存档。

开局导入的世界书使用 `layer=base_import`，并保存来源书名、来源格式和原条目 ID。导入人物卡的扩展字段保留在 `character_card.data` 中；页面确认的姓名、身份、性格和第一句话覆盖导入文件中的同名字段。

## 剧本名称修改

`LocalStoryStore.renameAdventure()` 使用 `BEGIN IMMEDIATE` 同时更新 `campaigns.name`、对应会话显示名以及修改时间。名称修改不写入剧情回合或状态变化，也不修改世界书、人物卡和历史内容；任一更新失败时整个操作回滚。

## 并发与重复提交

- 调用方必须提供 `expectedHeadTurnId`。分支已经前进时，提交会抛出 `BranchHeadConflictError`，不会覆盖新剧情。
- 调用方可以提供 `idempotencyKey`。网络重试或重复点击使用相同键时，返回第一次提交的回合，不会重复写入。
- 回合历史原则上只追加，不通过删除后续数据实现撤销。从旧回合继续或恢复存档时默认建立新分支，原路线保持不变。
- 玩家对恢复点执行"恢复"（`restoreSavePoint`）时属于明确的就地读档：在 `BEGIN IMMEDIATE` 事务内删除该分支在恢复点之后的回合（外键级联清理消息、事件、状态变化、重生成、管理变更、快照与记忆索引），用恢复点冻结的物化状态整体替换当前分支状态，并把分支头与下一回合序号改回恢复点位置。若恢复点属于其他分支则自动切换到该分支；若恢复点之后存在子分支分叉，恢复会被拒绝并要求改用"恢复为新分支"，避免破坏衍生路线。恢复后可在该分支继续推进新回合。

## 当前状态

所有可演化状态使用统一实体类型：

- `character_card`
- `character_state`
- `character_card_evolution`
- `world_book_entry`
- `relationship`
- `story_direction`
- `story_module`
- `plot_thread`（伏笔：dormant → seeded → paid_off）
- `plot_trigger`（偏离触发器：armed → fired，含强制状态影响）
- `plot_check`（属性判定结算记录）
- `location`
- `session_state`

支持 `replace`、`merge`、`activate` 和 `deactivate`。`merge` 使用 JSON Merge Patch 语义：对象递归合并、数组整体替换、`null` 删除字段。

## 数据库启动

数据库打开时自动：

- 创建数据目录。
- 开启外键检查。
- 使用 WAL 日志模式。
- 设置写入等待时间。
- 按顺序应用未执行的 SQL 迁移。
- 校验已执行迁移的 SHA-256，防止历史迁移被静默修改。

## 回合审计读取

加载最近回合时会同时读取该回合的 `state_changes`，并从叙述消息的本地元数据恢复模型名称和 token 用量。网页据此展示“本轮变化”，显示的是实际提交结果，而不是模型尚未落库的建议。

剧情页另外读取完整的轻量回合索引；选择不在最近缓存中的旧回合时，再按回合 ID 读取其完整剧情、台词、状态变化和用量。这些查询复用现有的回合顺序唯一索引与消息、事件索引，不新增重复状态表。

历史回看本身是只读操作，不移动分支头，也不会把旧候选项重新提交到当前剧情。玩家明确点击“从这里创建分支”后，系统才冻结所选回合结束时的状态并切换到新路线。

## 状态变更审计、字段锁与补偿回滚

`LocalStoryStore.loadStateAudit()` 按当前分支的实际提交顺序组合 `state_changes`、人物管理、地点管理、任务管理和 `state_control_changes`，逐项计算实体修改前与修改后的完整状态，再生成 JSON Pointer 字段差异。子分支从冻结的 `fork` 快照开始审计，因此父分支在分叉后的变化不会混入当前时间线。

玩家撤销一项变化时，系统不删除回合、消息、事件或原状态日志，而是在当前分支头追加一条 `state_control_changes`，以 `replace + result_active` 恢复该实体在原变化之前的完整状态。补偿记录本身也进入时间线，可以继续审计；开局基础资料禁止回滚。回滚使用 `actionId` 幂等执行，并与物化状态更新处于同一 `BEGIN IMMEDIATE` 事务。

字段锁通过追加式 `state_field_lock_changes` 保存，最新一条记录决定字段当前是否锁定。路径使用 JSON Pointer，`$active` 表示实体启停状态，`*` 表示整个实体。锁定是剧本级约束，对所有分支生效；玩家的手工管理和明确回滚不受限制。AI 回合提交或重生成时，存储层会保留已锁定旧值、提交其他未锁字段，并把被拦截路径及模型建议写入 `state_lock_blocks`，页面据此显示本轮被阻止的修改。

模型生成前会从启用的 `source_chunks` 中检索当前人物、地点、玩家输入、活动剧情任务和最近剧情最相关的少量片段。防剧透开启时，普通 `sourceReferences` 的 SQL 查询直接排除当前原作进度之后的片段。程序还提供两类导演引导（`upcomingScriptGuidance`）：一是任务活动 + 高度贴合时的防剧透导演锚点（`scope=next_chapter_director_only`），二是剧情与大纲一致（aligned）时的剧本推进引导（`scope=next_chapter_progress_hint`），都只从下一章节选择最多两个、总计不超过 3,600 字符，只能作为导演方向而不能作为已发生事实。实际普通引用和导演引导分别保存到 `generated_output_json.sourceReferences` 与 `generated_output_json.scriptGuidanceReferences`（引用对象带 `scope` 标注，旧存档缺省按导演锚点处理），便于历史审计；页面不展开引导正文以避免剧透。

原文进度支持"剧情驱动自动推进"：模型在回合输出顶层的可选 `sourceProgress` 字段报告剧情已推进到的原文章节号，本地在回合事务内校验后只进不退地更新启用且未删除文档的 `current_chapter`（收敛到各文档章节数），防剧透范围随之解锁。该变更写入 `content_asset_management_changes`（`operation='advance'`，只读审计、不可回滚、不阻断重生成），不写 `state_changes` 与 `materialized_states`。玩家仍可在原文资料设置中手动调整进度，自动推进不会把进度改小。

`turn_context_snapshots` 与 AI 回合一一对应，保存生成当时的完整系统消息、结构化上下文、实际基础请求消息、分区覆盖诊断、本地 token 估算和供应商输入 token。回合提交与快照写入处于同一事务；重生成以同一回合 ID 原子更新快照。页面通过独立回合接口按需读取，避免常规会话载入携带全部历史提示词。

## 剧情外人物管理

人物、地点、剧情任务、伏笔、触发器、世界书、原文、记忆和修改记录在页面上统一归入“剧本工作台”。其中前八类通过 `POST /api/adventures/{sessionId}/content` 的 `1.0.0` 协议共享命令信封、错误结构和最新内容快照；修改记录通过同一服务读取原文/记忆审计，通过专用状态接口执行跨领域状态回滚与字段锁。分支、存档、历史回看和回合重生成仍属于剧情时间线操作。完整协议见 [`CONTENT_SERVICE.md`](CONTENT_SERVICE.md)，玩家文件、内部记录和 API 上下文之间的转换规则见 [`FILE_LIFECYCLE.md`](FILE_LIFECYCLE.md)。

原文和记忆的统一管理由 `LocalStoryStore.manageContentAsset()` 执行。方法先按 `session_id + action_id` 检查幂等记录，再在一个 `BEGIN IMMEDIATE` 事务中修改 `source_*` 或 `memory_*` 数据、写入 `content_asset_management_changes` 并更新会话时间。相同动作安全复用；同一 `actionId` 搭配不同请求哈希会被拒绝。每个目标使用递增 `revision`；可恢复动作记录 `before_json` 与 `after_json`。回滚先核对活动分支头、最新修订、当前值与快照一致性，再恢复旧值、写入新的 `rollback` 动作并设置 `reverted_by_action_id`。原文删除只写 `is_deleted=1`，检索和目录查询会排除软删除记录。

人物管理不伪造剧情回合，也不移动分支头。一次操作会在同一个 `BEGIN IMMEDIATE` 事务中：

1. 追加 `character_management_changes` 审计记录。
2. 更新角色卡、当前状态、关系和会话人物登记的物化状态。
3. 更新会话修改时间。

请求使用 `actionId` 保证新增人物等网络重试不会重复执行。暂时离场只把 `present` 改为 `false`；角色卡仍会进入提示词，但模型不得让该角色无解释地参与当前场景。停用会同时停用角色卡、当前状态、演化层和相关关系，并从当前人物登记移除，因此后续模型输出不能再引用该角色。重新启用会恢复保存的资料。

人物管理以当前活动分支头作为状态版本参照，但不会修改该历史回合的 `state_changes`。历史状态重建会同时重放剧情状态变化、人物管理日志、地点管理日志、剧情任务管理日志、世界书管理日志和补偿式状态日志。

## 剧情外任务链管理

剧情任务管理不调用 DeepSeek，也不伪造剧情回合。新增任务默认处于 `queued` 状态；编辑会保留原任务 ID、顺序和进度，若编辑的是当前 `active` 任务，还会同步更新活动剧情走向。暂停使用物化状态的 `deactivate` 标记，使任务不再进入模型提示词或自动接续候选；重新启用不会重置任务进度。

任务 ID 在保存后不可修改。服务端会在同一事务内验证 30 个任务的数量上限、前置任务存在性、重复前置和循环依赖。当前任务不能暂停，`completed` 或 `diverged` 任务作为剧情历史禁止编辑和启停。每个请求使用 `actionId` 幂等写入 `story_module_management_changes`，失败时任务定义、活动剧情走向和会话状态一并回滚。

## 剧情外世界书管理

`LocalStoryStore.manageWorldBook()` 不调用 DeepSeek，也不建立剧情回合。每个请求使用 `actionId` 幂等写入 `world_book_management_changes`，并在同一 `BEGIN IMMEDIATE` 事务内更新 `materialized_states` 与会话时间；失败时全部回滚。

世界书的存储层级如下：

| `layer` | 用途 | 是否原位修改 |
| --- | --- | --- |
| `base` | 开局内置世界核心 | 否 |
| `base_import` | 玩家导入的基础世界书 | 否 |
| `session_overlay` | 已发生剧情产生的动态事实 | 可由后续剧情更新 |
| `player` | 玩家在工作台新增的条目 | 可编辑 |
| `player_override` | 玩家编辑、启停或软删除产生的修订层 | 可编辑、可撤销 |

编辑 `base` 或 `base_import` 时，系统复制当前字段建立 `player_override`，并用 `shadowsEntryId` 指向基础条目。提示词选择器先收集所有活动遮罩，再排除被遮罩基础条目；因此一个仍活动但 `enabled=false` 的覆盖层是“停用墓碑”，不会让旧基础事实重新进入 DeepSeek 上下文。“恢复基础版本”会停用同一基础条目的所有活动覆盖层。普通删除只写 `removedByPlayer=true` 和 `enabled=false`，不物理删除资料和审计历史。

## 剧情分支与存档恢复

每个会话通过 `sessions.active_branch_id` 记录当前活动分支。游戏读取、DeepSeek 生成、最新回合重生成、人物管理、地点管理和剧情任务管理全部只作用于该分支。

从历史回合创建分支时，系统在同一个事务中：

1. 验证起点回合属于当前可见历史。
2. 重放起点之前的剧情、人物管理、地点管理、剧情任务管理、世界书管理和补偿式状态变化。
3. 建立带 `parent_branch_id` 与 `forked_from_turn_id` 的新分支。
4. 把完整状态复制到新分支的 `materialized_states`。
5. 建立 `kind=fork` 的分支基线快照。
6. 把会话活动分支切换为新分支。

子分支只保存分叉后的新回合；读取历史时组合父分支截至分叉点的回合与子分支自己的回合。分支基线快照被冻结，因此父分支之后继续生成或手工修改人物、地点，都不会改变子分支的状态重建结果。主线（`branches.is_main=1`，每个剧本恰好一个）不能删除。

把任意支线"设为主线"（`setMainBranch`）时会在同一事务内重组分支树：新主线吸收父链各分支在分叉点之前的回合（回合 id 不变、序号按时间顺序重排），成为历史完整的主线根；原主线及其父链变为新主线的子分支（`parent_branch_id=新主线`），各自分叉点之后推进的回合保留并重排，没有自有回合的分支成为空分支（`head_turn_id` 指向分叉点回合、`next_sequence=1`，可从分叉点继续推进或删除）。被转移回合涉及的所有 `branch_id` 关联表（状态变更、各管理审计、锁定拦截、重生成、上下文快照、记忆检索、快照、恢复点）随迁到新主线；`materialized_states` 与记忆实体不复制，引用 id 稳定。状态重放按可见链位置过滤（分叉点引用变更先于自有变更），兼容新旧两套回合编号。分叉快照序号置 0（保证恢复到分叉点时删除全部自有回合）；自动快照与分叉快照同序号时保留分叉快照。

手动存档写入 `save_points`，内容包括当前全部物化状态，因此能够保留同一回合之后发生的手工人物、地点和剧情任务操作。恢复任何手动或自动存档都会建立新分支，不会移动或截断已有分支。系统在开局和每五个回合写入自动快照；最新回合重生成时，对应的自动快照会同步刷新。

## 地点与自动出场

地点使用 `location` 物化状态保存名称、描述和默认登场人物。当前位置写入 `session_state.currentLocationId`；各角色以 `character_state.present` 和 `character_state.locationId` 表达是否处于当前场景及最后所在地点。

DeepSeek 每轮返回 `sceneTransition`，其中包含回合结束时的地点和完整在场角色 ID。后端校验角色、地点与本轮证据后，在同一次回合事务中自动创建剧情发现的新地点、切换当前位置，并同步人物加入和离场。普通角色状态补丁不得直接修改 `present` 或 `locationId`，避免两个来源互相覆盖。

`sceneTransition.offstageUpdates` 可以让不在场角色显式移动位置（返回宅邸、前往城外）：目标角色必须不在本回合在场阵容中，进入已有地点沿用其 ID，进入新地点需提供名称；后端自动建立新地点实体并物化角色位置。剧本包 `adventure.locations` 可在开局预注册全部可能出现的地点（含常驻角色与重要性标记），未进入前即被声明；与开场地点同名的声明会被跳过。

玩家通过地点管理进行的新增、编辑、移动和启停不伪造剧情回合。操作写入 `location_management_changes`，并原子更新地点、当前位置和人物状态。每个地点可以配置默认登场 AI 人物；手工移动到该地点时，玩家角色始终随行，默认人物登场，其他人物暂时离场。网络重试使用 `actionId` 保证幂等。

## 游戏内时间与任务期限

`session_state.core.gameTimeDay` 表示游戏内第几天，开局为第 1 日。游戏内时间只由剧情推进驱动：`sceneTransition.timeAdvance` 缺省视为时间基本不变（相当于 `moment`），不推进天数；`hours` 不推进天数、`one_day` 推进一天、`several_days` 推进约数日。时间推进与回合状态变化在同一事务内提交，历史回合通过其 `stateChanges` 可还原当时的日期。

剧情任务可声明 `deadlineDay`（游戏内期限）。每回合组装提示词时，活动且已到期的任务作为 `expiredDeadlines` 硬事实注入上下文，模型必须让期限后果在本轮显现；该机制与回合生成共用同一套校验与提交路径，不单独写库。

## 初始关系

剧本包 `adventure.initialRelationships` 在开局物化时建立关系基线：每条声明自动生成正向与反向两条 `relationship` 记录（A→B 与 B→A 独立演化，数值一致；声明中已显式给出反向的以声明为准）。关系实体通过 `sourceCharacterId:targetCharacterId` 标识，五个维度（信任、好感、恐惧、敌意、敬意）均为 -100 ~ 100。未声明的角色关系保持中性（0）并标记“关系尚未建立”。

## 最新回合重生成

重生成不会继续追加新回合。系统先从剧情状态变化、人物管理、地点管理、剧情任务管理和补偿式状态日志重建最新回合开始前的物化状态，再使用原回合的玩家输入调用当前模型。旧版最新回合会以不可信、尚未发生的待替换草稿进入重写请求，便于玩家精确调整其中 AI 控制角色和 NPC 的动作、台词与结果；它不会进入更早历史或被当成必须保留的事实。新结果通过完整校验后，在一个 `BEGIN IMMEDIATE` 事务中：

1. 恢复上一回合结束时的物化状态。
2. 替换最新回合的生成输出、消息、事件与状态变化。
3. 应用新结果产生的全部状态变化。
4. 更新该回合的实际上下文快照。
5. 把替换前后的结构化结果以及玩家本次修改意见写入 `turn_regenerations`。

分支头、回合 ID 和回合序号保持不变，因此历史索引不会多出一个伪回合。`actionId` 保证网络重试不会再次调用模型或重复替换；重生成期间若分支继续前进、另一轮重生成已经完成，事务会因版本冲突而停止。若最新回合之后存在人物、地点、剧情任务、世界书、原文、记忆或补偿回滚记录，系统会在调用模型前阻止重生成，避免覆盖玩家明确修改的内容。字段锁不阻止重生成，而是在新结果提交时继续保护锁定值并记录拦截结果。

## 删除剧本

删除操作在事务中删除选中的本地会话。SQLite 外键级联会同时清理分支、回合、消息、事件、剧情状态变化、人物、地点、任务、世界书、原文与记忆管理日志、补偿回滚、字段锁、锁定拦截、重生成记录、物化状态和快照；如果该战役已经没有其他会话，战役记录也会一并删除。网页必须先显示不可撤销确认，取消确认时不会发送删除请求。

## 完整存档与整库恢复

单剧本完整存档使用 `ai_tavern_runtime_archive_v1`，覆盖该会话关联的全部运行表。当前导出文件使用 `schemaVersion=1.9.0`，在 `1.8.0` 基础上新增 `branches.is_main` 主线标志；`1.8.0` 及更早旧存档仍可导入（旧档缺少 `is_main` 时按"根分支即主线"派生）。`1.7.0` 的内容动作缺少恢复字段时会以只读历史导入，缺失新表的更早版本按空记录处理，旧版长期记忆也会在首次打开时补建。文件包含数据区 SHA-256；导入前校验字段、JSON 内容、分支/回合/原文/回滚来源引用和校验值。导入在一个 `BEGIN IMMEDIATE` 事务中完成，并为数据库主键、上下文 JSON 内的回合引用、内容动作目标和操作幂等 ID 建立新映射，所以可以在同一数据库中创建隔离副本。任何插入或外键检查失败都会回滚。

## 长剧情记忆与上下文预算

每个剧情分支独立维护三类记忆数据：`memory_entries` 保存事实、关系、角色长期变化、未解决线索和承诺；`memory_chapters` 按设置的回合数保存阶段摘要；`memory_retrievals` 记录一次模型生成实际使用的记忆 ID、章节 ID、查询和估算 token。`memory_settings` 默认提供 2400 token 长期记忆预算、6 个最近回合和每章 10 回合，玩家可以在游戏页调整。

自动提取只读取已经提交的结构化事件、状态变化、玩家承诺和剧情走向，不进行额外模型调用。检索以玩家本轮选择、言行、剧情走向和重生成意见为查询；匹配关键词的旧事实、仍生效的承诺或线索和玩家固定的记忆进入候选，再按预算截断。最近回合另行保留，当前状态中的人物卡、地点和世界书也按在场性、常驻性与本轮相关性控制预算。回合提交、重生成和新分支建立都在原事务内同步记忆；手工修正会转为玩家维护版本，自动重建不会覆盖。

整库恢复与单剧本导入不同：它使用 SQLite `VACUUM INTO` 生成的一致性 `.sqlite` 文件替换当前整库。恢复前先自动建立 `pre-restore` 安全备份；替换失败时系统会用该安全备份回滚。该流程只操作 `AI_TAVERN_DATA_DIR` 下经过严格文件名校验的备份文件。
