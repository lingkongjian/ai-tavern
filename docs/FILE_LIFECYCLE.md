# AI 酒馆内容文件生命周期与规范

版本：`1.6`

状态：当前工程的权威文件处理规范。后续新增导入格式、内部存储表、模型上下文分区或导出类型时，必须先更新本规范，再同步玩家操作手册和对应 Schema。

## 1. 目的与适用范围

本规范统一三类容易混淆的数据：

1. 玩家提供给程序的文件；
2. 程序在本机内部保存的数据和文件；
3. 程序经过筛选后发送给当前模型供应商 API 的请求内容。

三者不能直接等同。玩家选择一个文件，不代表该文件会原样进入数据库或完整发送给模型；数据库记录也不代表每轮都会进入模型上下文。

本规范覆盖人物卡、世界书、开局剧本包、拆分剧本项目、原文参考、完整运行存档、模型目录清单、SQLite 数据库与备份、长期记忆、上下文快照和模型供应商请求消息。

## 2. 规范词

- **必须**：实现和资料都不得违反。
- **应当**：默认遵守，只有明确记录理由时才可偏离。
- **可以**：可选能力。
- **源文件**：玩家或剧本作者维护的原始内容。
- **规范对象**：解析并转换成程序统一结构后的对象。
- **运行状态**：SQLite 中随剧情变化的正式记录。
- **API 上下文**：某一回合实际发送给当前模型供应商的消息与结构化资料。
- **发布物**：可脱离作者维护目录独立导入的文件。

## 3. 唯一处理流水线

所有新增文件类型都必须接入同一条流水线，不得在页面组件中直接解析后写库：

```text
玩家选择文件
  → 文件名、扩展名、大小与 UTF-8 检查
  → JSON 或文本语法解析
  → 可选：明确授权后发送原文或代表片段，分析人物与开场候选
  → 玩家确认玩家角色、主要 AI 角色和开场章节
  → 可选：再次发送同一范围原文，生成受确认结果约束的结构蓝图
  → 可选：填写修改意见，只重新生成并合并一个剧本包分区
  → 兼容格式识别
  → 规范化为内部输入对象
  → Schema 与跨对象语义校验
  → 玩家预览和确认
  → 单事务写入 SQLite
  → 运行时相关性检索与预算裁剪
  → 组装模型供应商请求
  → 记录本轮实际上下文快照
```

失败时遵循以下边界：

- 解析或校验失败：不得写入数据库；
- 数据库任一写入失败：回滚整个操作；
- 模型供应商请求失败：不得提交半个剧情回合；
- 模型输出校验失败：最多执行一次结构修复，仍失败则保留原存档；
- 导出或构建失败：不得覆盖上一个有效发布物。

## 4. 三类数据的边界

### 4.1 玩家提供的文件

| 类型 | 推荐格式 | 进入入口 | 是否可以直接编辑 | 是否整份发送给模型供应商 |
| --- | --- | --- | --- | --- |
| 人物卡 | UTF-8 JSON，Character Card V2 | 新建剧本导入区 | 导入预览后可改基础字段 | 否，按当前人物相关性选取角色卡和状态 |
| 世界书 | UTF-8 JSON，`ai_tavern_world_book_v1` | 新建剧本导入区 | 导入预览后可改开局表单；运行中在工作台逐条编辑和比较层级 | 否，只发送常驻或本轮相关条目 |
| 完整剧本包 | UTF-8 JSON，`ai_tavern_adventure_bundle_v1` | 新建剧本导入区 | 载入表单后可逐项调整 | 否，拆成角色、世界、任务、原文等分区 |
| 用于生成剧本包的原文 | UTF-8 `.txt` 或 `.md` | 新建剧本“AI 原文分析” | 分析后先确认分工，生成后可编辑或按分区重做 | 分析、正式生成及每次分区重做都会发送；每次短文整份、长文最多 48,000 字符 |
| 拆分剧本项目 | 目录与 `开局预设.json` | 本地构建脚本 | 是，作为作者唯一编辑源 | 不直接发送，也不能直接在网页整体导入 |
| 原文参考 | UTF-8 `.txt` 或 `.md` | 游戏内剧本工作台 | 可修改进度、启停和贴合度；进度也可随剧情推进自动解锁（只进不退）；正文需重新导入 | 否，只发送少量检索片段 |
| 完整运行存档 | UTF-8 JSON，`ai_tavern_runtime_archive_v1` | 首页完整存档区 | 不建议手工编辑 | 不直接发送；导入后恢复为运行状态 |
| 模型供应商配置 | 开发版 `.env.local`；桌面版 `用户数据/配置/模型.env` | 主菜单“API 配置”或手工配置 | 是；网页删除只移除五项 AI 连接变量，保留其他变量 | API Key 只用于请求鉴权，不得进入消息正文或返回浏览器 |
| 模型目录清单 | UTF-8 JSON，`ai_tavern_model_catalog_v1` | “API 配置”读取后导出 | 只读诊断文件 | 不发送；不含 API Key，也不能导入为运行配置 |

通用约束：

- JSON 与文本必须使用 UTF-8；建议不带 BOM。
- JSON 文件不得包含注释、脚本、宏、模板执行指令或外部资源加载指令。
- 人物卡、世界书普通单文件不超过 1 MB。
- 完整剧本包不超过 5 MB。
- 用于自动生成剧本包的原文至少 200 字符、最多 900,000 字符，浏览器文件不超过 3.5 MB。
- 完整运行存档不超过 100 MB。
- 每个剧本最多保存 5 份原文参考；每份正文不超过 200 万字符。
- 开局世界书总计不超过 200 条；剧情任务不超过 30 个。
- 文件名只用于显示和来源追踪，不得作为读取其他本地文件的隐式路径。

### 4.2 程序内部保存的数据与文件

正式数据源是本机 SQLite，而不是浏览器缓存。

源码开发模式使用项目 `data/`；macOS 桌面模式使用软件同级 `用户数据/数据/`，并把配置、缓存、日志、崩溃报告和临时目录一并放入 `用户数据/`。桌面安装包只带空目录说明，不带测试剧本、开发数据库或 API 配置。玩家主动导出到其他位置的文件不受该内部目录约束。

```text
data/
├── ai-tavern.sqlite       # 当前正式数据库
└── backups/               # SQLite 一致性备份
```

主要内部记录：

| 数据 | 保存位置 | 性质 | 可否手工改文件 |
| --- | --- | --- | --- |
| 剧本、会话、分支与回合 | SQLite | 正式运行记录 | 不应直接修改数据库 |
| 基础角色卡与世界书 | `materialized_states` 及变化日志 | 规范化后的内容状态 | 通过剧本工作台修改 |
| 角色状态、关系、地点、任务 | 状态变化日志与物化状态 | 可审计的当前值 | 通过工作台或剧情提交修改 |
| 原文全文与切片 | `source_documents`、`source_chunks` | 本地检索资料 | 通过原文栏目管理 |
| 长期记忆与章节摘要 | `memory_*` | 从已发生剧情提炼的上下文 | 通过记忆栏目修正、固定或停用 |
| 自动快照和手动存档 | `snapshots`、`save_points` | 恢复点 | 通过分支与存档管理 |
| 实际模型上下文 | `turn_context_snapshots` | 回合级不可追溯重建的请求证据 | 只读查看；重生成成功时更新 |
| 完整运行存档 | 玩家导出的 JSON | 单剧本迁移发布物 | 不建议手工修改 |
| 整库备份 | `data/backups/*.sqlite` | 整机本地恢复文件 | 不应使用 SQLite 工具直接编辑 |

内部数据必须保留来源：

- 导入角色卡保留兼容格式与未知扩展字段；
- 世界书保留来源书名、原条目 ID 和格式；
- 剧情生成的持久变化记录来源回合与证据 ID；
- 玩家手工修改记录独立的 `actionId`、时间和原因；
- 模型上下文快照记录模型、请求次数、token、系统消息和具体分区。

### 4.3 发送给模型供应商 API 的内容

程序不会上传 SQLite 文件、完整运行存档或备份文件。剧情回合生成只发送 `messages` 数组，其中包含：

1. 系统消息：输出协议、玩家控制边界、角色与状态同步规则；
2. 用户消息：经过规范化和预算选择后的结构化故事上下文；
3. 重新生成时的玩家修改意见；
4. 首次结构校验失败时，可能附加上一版 JSON 和结构修复问题。

首页原文生成剧本包是独立的创建前流程，不使用当前剧本数据库上下文。分析阶段最多发送 48,000 字符：短文发送完整正文，长文按章节切片后选择开篇、全书分布和结尾的代表片段；它只返回人物与开场候选，不改变表单。玩家确认玩家角色、主要 AI 角色和开场章节后，正式生成再次发送相同范围的原文和确认约束。生成后每次分区重做会再次发送同一范围原文、确认约束、所选分区当前版本和必填修改意见。每次生成第一次结构校验失败时，最多再发送上一版 JSON 与问题列表修复一次。完整原文由本地程序直接写入生成包，不要求模型复述；成功结果只填入浏览器草稿，不自动写入 SQLite。

结构化故事上下文的标准分区：

| 分区 | 来源 | 选择规则 |
| --- | --- | --- |
| `campaign` / `session` / `branch` | 当前剧本和分支 | 当前会话固定进入 |
| `characterDirectory` | 启用角色 | 提供 ID、姓名、身份、在场和位置索引 |
| `activeStates` | 角色卡、角色状态、演化、关系、地点、世界书、剧情走向 | 按在场性、常驻性、玩家输入相关性和状态预算选择 |
| `storyModules` | 启用的剧情任务 | 只包含当前任务与可能接续的就绪任务 |
| `recentTurns` | 当前分支近期回合 | 按记忆设置保留最近若干回合 |
| `chapterSummaries` | 长剧情章节摘要 | 召回相关阶段摘要 |
| `longTermMemory` | 长期记忆 | 按关键词、状态、重要度、固定标记和 token 预算选择 |
| `sourceReferences` | 原文检索切片 | 按人物、地点、玩家输入、原作进度和防剧透设置选择少量片段 |
| `upcomingScriptGuidance` | 下一章节导演锚点 | 仅在高度贴合的活动剧本任务中选择，用于约束重大方案；不得作为已发生事实 |
| `playerInput` | 三种输入框和候选项 | 当前回合完整进入 |

绝对禁止发送：

- `AI_API_KEY` 或其他本地密钥；
- SQLite 数据库、备份文件和完整存档原文件；
- 与当前会话无关的其他剧本内容；
- 本地文件绝对路径；
- 剧情回合中未经检索选择的整本原文；原文生成入口中由玩家明确选择且不超过 48,000 字符的短文除外；
- 浏览器缓存、系统日志或开发环境隐私数据。

### 4.4 模型目录清单

模型目录清单是设置界面从供应商 `/models` 响应规范化后的本地导出物，不是剧本内容，也不是密钥备份：

- `schemaVersion` 固定为 `1.0.0`；
- `kind` 固定为 `ai_tavern_model_catalog_v1`；
- 必须包含 `provider`、`providerLabel`、`baseUrl`、`catalogFetchedAt`、`exportedAt`、`selectedModel`、`verifiedModel`、`summary`、`audit` 和完整 `models` 数组；
- `summary` 固定统计 `chatCompletionsCandidates`、`requiresAudit` 与 `unsupportedProtocol`；
- 每个模型必须包含稳定 `id`、显示名称、`compatibility` 与判定说明；
- `compatibility` 只能是 `chat_completions`、`unknown` 或 `unsupported_protocol`；
- 可选 `audit` 只记录当前所选模型的分项审核；`verifiedModel` 仅在该模型审核通过时填写；
- 文件绝对不得包含 API Key、Authorization 请求头、系统提示、玩家资料或供应商原始错误正文。

模型目录只反映读取当时供应商返回的模型范围；即使 `compatibility=chat_completions`，也仍需用当前 token 审核生成权限。此文件不进入 SQLite、完整存档、剧本包或模型上下文，未来导入或分享后不能自动恢复密钥和可用状态。

权威结构见[《模型目录清单 JSON Schema》](../public/文件标准/模型目录清单.schema.json)。

## 5. 规范化规则

### 5.1 人物卡

内部基准为 Character Card V2 数据模型。V3 与旧版扁平 JSON 可以导入，但必须先规范化：

- 姓名、描述、性格、场景、开场消息和对话示例进入标准字段；
- 未识别的安全扩展保留在 `data.extensions`；
- 页面明确编辑的姓名、身份、性格和开场消息优先于导入卡同名字段；
- 玩家卡不得预先决定玩家的言行、同意、承诺或感情；
- AI 角色卡应把稳定性格与临时状态分开。

### 5.2 世界书

内部基准为 `ai_tavern_world_book_v1`：

- 长期客观事实写世界书；短期心情、位置和当前目标写角色状态；
- `constant=true` 只用于每轮都必须知道的核心规则；
- 非常驻条目必须有明确关键词；
- AI 产生的持久变化写入动态覆盖层，不直接破坏玩家导入的基础层；
- 被动态层覆盖的旧条目不能重复进入模型上下文。
- `base` 与 `base_import` 是不可变基础层；玩家编辑它们时建立 `player_override` 修订层，而不是原位覆盖；
- 玩家新增条目使用 `player` 层；再次编辑、停用或软删除后进入可审计的 `player_override` 层；
- 修订层用 `shadowsEntryId` 指向被覆盖的基础条目；即使修订层被停用，它仍作为有效遮罩阻止旧事实重新进入上下文；
- “恢复基础版本”会停用同一基础条目的活动覆盖层，使基础内容重新生效；界面按字段展示基础值与当前值差异。

### 5.3 开局剧本包

完整剧本包是独立发布物，必须内嵌：

- 玩家角色、主要角色和其他角色的完整卡；
- 世界书完整对象；
- 原文参考实际正文；
- 剧情任务链；
- 开场地点、可直接阅读的开场正文和初始剧情走向。

包中的文件名不能作为外部依赖。作者应维护拆分项目，由构建脚本生成完整包和 SHA-256 校验报告。

玩家也可以在首页上传原文自动得到同一种标准包。第一阶段分析并展示人物与开场候选；玩家确认分工后，模型才生成受限蓝图。程序强制核对确认的人物姓名和开场章节，负责标准对象、稳定 ID、任务前置、完整原文内嵌和最终校验。生成后可凭必填修改意见单独重做角色、世界书、剧情任务或开篇：程序只合并目标分区并复验整包，网页先按项目比较当前表单与 AI 新版本。只有玩家明确采用后才刷新目标字段和下载基线；放弃、校验失败或预览期间目标内容已变化时，当前数据保持不变。生成包属于创建前草稿，玩家确认并创建剧本后才写库。后续手工表单编辑不会暗中反写 JSON。

### 5.4 原文参考

- 原文正文原样保存在本地，不改写为提示词摘要；
- 导入时按 Markdown 标题、章节标题或场景边界切片；
- `currentChapter` 表示允许检索到的进度；
- `preventFuture=true` 时，未来章节会从普通原文引用查询中排除；
- 活动剧本任务采用 `faithful` 时，可以从紧邻的下一章节提取最多两个受限导演锚点，避免模型自行发明与原作冲突的重大方案；
- 导演锚点只约束核心机制、必要参与者、条件和因果，不向角色自动授予知识，不把未发生原作剧情变成本剧本事实，也不会在普通回合引用界面展开正文。

### 5.5 完整运行存档

- 当前版本：`schemaVersion=1.9.0`，包含原文与记忆内容动作审计、恢复快照、修订序号、原文软删除状态、伏笔/偏离触发器/属性判定的管理审计表，以及 `branches.is_main` 主线标志；
- 文件必须含 SHA-256 完整性字段；
- 导入时校验所有表、JSON 字段和内部引用；
- 导入生成全新内部 ID，并创建名称带“（导入）”的隔离副本；
- 旧版本按兼容表清单补空，不伪造不存在的历史上下文。

## 6. 优先级与冲突解决

同一事实出现冲突时按以下优先级处理：

1. 当前回合玩家明确输入；
2. 已提交的较新剧情事实与玩家手工确认状态；
3. 字段锁和当前物化状态；
4. 角色演化层与动态世界书覆盖层；
5. 基础角色卡和基础世界书；
6. 已召回的长期记忆和章节摘要；
7. 原文参考中尚未在本剧本发生的内容；
8. 剧情任务中的未来规划。

剧情走向、剧情任务和原文进度属于导演或系统信息，NPC 不得自动知晓。

## 7. 版本、命名与完整性

### 7.1 版本字段

| 对象 | 格式版本字段 | 内容版本字段 |
| --- | --- | --- |
| 人物卡 | `spec_version` | 可放作者扩展 |
| 世界书 | `spec_version` | 可放作者扩展 |
| 完整剧本包 | `spec_version` | `bundle_version` |
| 拆分项目 | `spec_version` | `bundle.version` |
| 完整运行存档 | `schemaVersion` | 不单独维护内容版本 |
| 模型目录清单 | `schemaVersion=1.0.0` | 不适用 |
| AI 回合输出 | `schemaVersion=1.0.0` | 不适用 |

格式版本与内容版本不得混用。格式没有变化时，更新剧情内容只增加内容版本。

### 7.2 文件命名

推荐使用中文可读名称和稳定前缀：

```text
人物卡/00_玩家角色_姓名.json
人物卡/01_主要角色_姓名.json
世界书_剧本名称.json
原文参考_剧本名称.md
完整剧本包_剧本名称.json
校验报告_剧本名称.json
完整存档_剧本名称_日期.json
```

文件内 ID 使用稳定的小写 ASCII、数字、短横线或明确 UUID；显示名称可以使用中文。发布新版本时不得仅因改名而改变稳定 ID。

## 8. 安全与隐私

- `.env.local`、`data/`、备份、玩家原文和运行存档不得提交到 Git。
- API Key 只能在本地服务端读取，不得使用 `NEXT_PUBLIC_` 前缀。
- 文件导入器不得执行脚本、宏或外部命令。
- 相对路径必须解析在剧本维护目录内，禁止 `..` 路径越界。
- 删除原文使用软删除：不会参与后续检索，也不会删除正文、切片、已经写入历史回合的引用片段或上下文快照。在剧情尚未继续且同一资料没有后续修改时，可以从“修改记录”恢复。
- 完整存档可能包含玩家全部剧情与原文，分享前必须由玩家自行确认内容范围。

## 9. 新功能接入工作台的规则

所有新的“剧本内容编辑”功能必须接入游戏页的“剧本工作台”，不得再建立孤立入口。当前栏目：

| 栏目 | 管理对象 | 允许的操作 |
| --- | --- | --- |
| 人物 | 基础角色卡、启用、在场 | 新增、编辑、出场、停用 |
| 地点 | 地点资料、默认阵容、当前位置 | 新增、编辑、移动、启停 |
| 剧情任务 | 目标、条件、前置和接续 | 新增、编辑、暂停、恢复 |
| 伏笔 | 跨章节伏笔的埋设与回收条件 | 新增、编辑、删除 |
| 触发器 | 偏离原剧情时的意外阻碍与强制状态影响 | 新增、编辑、删除 |
| 世界书 | 基础、导入、剧情动态与玩家修订层 | 新增、编辑、筛选、启停、软删除、比较差异、恢复基础版本 |
| 原文 | 原文文件、进度、防剧透、贴合度 | 导入、设置、启停、软删除、安全撤销 |
| 记忆 | 长期记忆、章节摘要和预算 | 修正、固定、解决、停用、重建 |
| 修改记录 | 原文、记忆、角色演化、关系、地点、世界书、剧情走向等变化 | 审计、安全撤销、补偿回滚、字段锁 |

人物、地点、剧情任务、伏笔、触发器、世界书、原文和记忆的浏览器操作必须使用 [`CONTENT_SERVICE.md`](CONTENT_SERVICE.md) 定义的统一 `1.0.0` 命令信封。服务返回本地最新的剧本、原文目录、记忆和审计快照；工作台不得只在浏览器内拼接局部结果。原文与记忆撤销继续使用统一内容命令；跨领域状态回滚与字段锁使用专用接口，但在同一“修改记录”栏目展示。

分支、存档、历史回看和回合重生成不属于内容编辑：它们继续保留在剧情时间线区域，但必须在操作手册中说明与工作台修改的相互影响。

## 10. 文档同步矩阵

每次功能更新必须根据影响范围同步以下文档：

| 变更 | 必须同步 |
| --- | --- |
| 新增或修改玩家文件格式 | 本规范、`IMPORT_FORMAT.md`、对应 JSON Schema、示例、操作手册 |
| 修改内部数据库结构 | 本规范、`STORAGE.md`、迁移、完整存档版本与 Schema、自动化测试 |
| 修改模型供应商或请求内容 | 本规范、`DEEPSEEK.md`、`GENERATION_SPEC.md`、上下文快照测试、操作手册 |
| 新增剧本编辑功能 | 统一内容服务、工作台标签或既有栏目、本规范功能表、操作手册、界面测试 |
| 修改玩家操作流程 | 操作手册、README 快速说明、浏览器回归测试 |
| 修改备份、导入或恢复行为 | 本规范、操作手册、`LOCAL_RUNTIME.md`、往返测试 |

提交前检查：

- [ ] 功能能从统一工作台或明确的时间线入口找到；
- [ ] 输入先规范化和校验，再写入数据库；
- [ ] API 只获得本轮必要内容；
- [ ] 新字段有来源、版本和兼容策略；
- [ ] 失败不会留下部分状态；
- [ ] Schema、示例、工程规范和玩家手册已经同步；
- [ ] 自动化测试覆盖正常、失败、旧版兼容和导入导出往返；
- [ ] 浏览器完成桌面与窄屏验证。
