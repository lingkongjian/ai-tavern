# AI 酒馆导入材料文件结构指导手册

版本：`1.9`

本手册规定人物卡、世界书、原文参考、剧情任务和完整剧本包在制作、维护与发布时的文件组织方式。字段的完整定义仍以同目录的 JSON Schema 和 [`docs/IMPORT_FORMAT.md`](../../docs/IMPORT_FORMAT.md) 为准；玩家文件、程序内部记录与当前模型供应商请求之间的边界以[内容文件生命周期与规范](../../docs/FILE_LIFECYCLE.md)为准。

## 一、先区分四种交付物

### 1. 可直接导入的完整剧本包

完整剧本包是一个 `.json` 文件。玩家只需在“导入或生成剧本资料”中选择这一个文件。

它必须把以下内容全部内嵌在 `adventure` 中：

- 玩家人物卡、主要角色卡和其他角色卡；
- 世界书；
- 原文参考的实际文本；
- 剧情任务模块；
- 开场地点、开场正文和初始剧情走向。

`fileName`、人物卡文件名等字段只用于记录来源和显示，不会让程序读取同目录的其他文件。完整包不能依赖相对路径才能导入。

### 2. 便于创作与维护的拆分资料目录

拆分目录供作者逐项修改、审阅和版本管理。它不是一个可被程序整体解析的压缩包；发布前需要把其中内容组装成一个完整剧本包，或者分别在页面上导入。

### 3. 完整运行存档

完整运行存档由程序在已有剧本旁自动导出，用于迁移已经游玩的剧情、分支和动态状态。它不属于创作资料，不建议手工编辑，也不能用拆分目录替代。

### 4. 由原文自动生成的剧本包草稿

玩家可以在首页“AI 原文分析”中上传 UTF-8 TXT/Markdown。第一阶段只展示人物、推荐分工和开场候选；玩家确认玩家角色、主要 AI 角色和开场章节后，第二阶段才生成世界书、任务链与开场蓝图。程序会拒绝擅自更换确认角色或章节的输出，再负责生成稳定 ID、规范对象、内嵌完整原文并用同一个剧本包导入器校验。成功结果与手工制作的 `ai_tavern_adventure_bundle_v1` 完全使用同一结构，可以下载、再导入或作为拆分维护项目的起点。

该方式适合快速起稿，不替代人工审核。人物分工和开场先由玩家确认；人物在场状态、世界事实和任务拆分仍应在创建前检查。生成后可以填写必填修改意见，只重做角色资料、世界书、剧情任务或开篇。模型仍生成完整候选蓝图，但程序只合并所选分区并再次校验完整包。网页先展示当前表单与 AI 新版本的项目级差异，玩家明确采用后才替换目标字段；放弃或预览冲突不会修改内容。分析结果只存在当前页面，刷新后不会恢复。下载按钮保存最近一次已经采用并通过校验的生成基线；待确认结果、已放弃结果和网页表单后续手工修改都不会反写 JSON。

## 二、推荐的维护目录

```text
剧本名称/
├── README.md
├── 开局预设.json
├── 完整剧本包_剧本名称.json
├── 校验报告_剧本名称.json
├── 世界书_剧本名称.json
├── 原文参考_剧本名称.md
└── 人物卡/
    ├── 00_玩家角色_姓名.json
    ├── 01_主要角色_姓名.json
    ├── 02_其他角色_姓名.json
    └── ...
```

- `README.md`：说明故事范围、导入方式、角色分工、任务链和原文进度。
- `开局预设.json`：符合 `ai_tavern_bundle_project_v1` 的组装清单，集中保存战役表单、剧情任务和文件对应关系；它不是网页直接导入类型，由本地构建器读取。
- `完整剧本包_剧本名称.json`：最终发布物，必须能脱离同目录文件独立导入。
- `校验报告_剧本名称.json`：自动记录完整包摘要、SHA-256、资料数量、检查项目和兼容提示。
- `世界书_剧本名称.json`：世界书的单独源文件。
- `原文参考_剧本名称.md`：供检索的人物和剧情参考原文。
- `人物卡/`：一人一张卡。数字前缀只用于固定阅读顺序，不属于人物卡格式。

建议把拆分文件作为内容的唯一编辑源，把完整剧本包视为发布产物。修改拆分文件后重新组装并校验完整包，不要长期同时手工维护两套不同内容。

## 三、开局预设与自动构建

`开局预设.json` 使用以下顶层结构：

| 字段 | 用途 |
| --- | --- |
| `spec` | 固定为 `ai_tavern_bundle_project_v1` |
| `spec_version` | 固定为 `1.0` |
| `bundle` | 发布包名称、说明、作者、内容版本、输出文件和报告文件 |
| `campaign` | 世界、玩家说明、角色姓名校验、开场、剧情任务链、初始关系、初始状态与地点清单 |
| `materials` | 人物卡、世界书和原文参考的项目内相对路径 |
| `source` | 可选的原作来源、归一化说明等作者元数据 |

`materials.additionalCharacters` 中每个角色必须明确设置 `file` 和 `presentAtOpening`。需要避免其人物卡开场台词自动出现在第一幕时，再设置 `firstMessage` 为空字符串。原文参考必须在 `materials.referenceDocuments` 中同时设置文件、显示名称和当前进度。

`campaign` 除了世界与开局字段外，还可以在 `storyModules` 的每个任务中设置 `deadlineDay`（游戏内期限），并提供可选的 `initialRelationships`（按角色姓名声明开局关系，自动建立双向记录）、`initialStatuses`（按角色姓名声明开局状态词条：受伤/中毒/增益等 buff/debuff，角色未察觉的标 `hidden`）与 `locations`（预注册剧本中可能出现的地点，含常驻角色与重要性标记）。构建器会校验这些字段的角色引用与数值范围。

完整字段见 [`剧本包项目.schema.json`](./剧本包项目.schema.json)，可公开使用的最小实例见本手册末尾的标准示例。

在项目根目录运行：

```bash
# 只检查，不修改文件
npm run bundle:check -- "你的剧本资料目录"

# 检查通过后，分别原子更新完整剧本包和校验报告
npm run bundle:build -- "你的剧本资料目录"
```

也可以直接运行 `node scripts/构建剧本包.mjs <项目目录或开局预设.json>`。使用 `--output` 和 `--report` 可以覆盖输出位置。

构建器会检查：

- 所有资料路径都位于维护目录内，且文件存在、编码与 JSON 语法有效；
- 人物卡、世界书、原文参考及最终完整包都能被项目导入器解析；
- 清单中的玩家和主要角色姓名与人物卡一致，全部角色姓名不重复；
- 世界书条目 ID 不重复；
- 剧情任务 ID、前置任务和初始任务存在，前置关系不形成循环；
- 最终文件没有外部路径依赖，并输出 SHA-256、资料数量和兼容提示报告。

任何检查失败时都不会覆盖现有完整包或报告。

## 四、完整剧本包的对象层级

```text
根对象
├── spec = ai_tavern_adventure_bundle_v1
├── spec_version = 1.1
├── name / description / creator / bundle_version
└── adventure
    ├── campaignName / campaignDescription / world
    ├── player
    │   └── card
    ├── mainCharacter
    │   └── card
    ├── additionalCharacters[]
    │   ├── card
    │   ├── firstMessage
    │   └── presentAtOpening
    ├── worldBook
    ├── referenceDocuments[]
    ├── storyModules[]
    ├── initialRelationships[]      （可选）
    ├── initialStatuses[]          （可选）
    ├── locations[]                 （可选）
    └── opening
        ├── locationName
        ├── scene
        ├── initialStoryDirection
        └── initialStoryModuleId
```

各拆分文件与完整包字段的对应关系如下：

| 拆分资料 | 完整包中的位置 |
| --- | --- |
| 玩家人物卡 | `adventure.player.card` |
| 主要角色人物卡 | `adventure.mainCharacter.card` |
| 其他角色人物卡 | `adventure.additionalCharacters[].card` |
| 世界书 | `adventure.worldBook` |
| 原文参考正文 | `adventure.referenceDocuments[].content` |
| 剧情任务清单 | `adventure.storyModules` |
| 初始关系清单 | `adventure.initialRelationships`（按角色姓名引用，自动建立双向关系） |
| 初始状态清单 | `adventure.initialStatuses`（按角色姓名引用，物化为开局状态词条，隐藏状态探索解锁） |
| 地点清单 | `adventure.locations`（开局预注册，未进入前即被声明） |
| 开局表单 | `adventure.opening` 及战役基础字段 |

## 五、人物卡文件

人物卡推荐使用 Character Card V2：

- `spec` 固定为 `chara_card_v2`；
- `spec_version` 固定为 `2.0`；
- 角色内容全部放在 `data` 中；
- 项目私有信息放在 `data.extensions` 中。

玩家卡应描述身份、能力、已知经历和开场状态，但不能替玩家预先决定言语、行动、承诺或感情。AI 角色卡应同时写清稳定性格、价值判断、说话方式、关系边界和行为动机，并用 `mes_example` 提供足够接近原作的对话示例。

完整包中的每个角色都必须内嵌完整 `card` 对象。其他角色还必须设置：

- `role`：角色在本剧本中的用途；
- `presentAtOpening`：是否在第一幕现场；
- 可选 `firstMessage`：覆盖人物卡的开场台词。设为空字符串可保留卡片资料但避免自动发言。

## 六、世界书文件

世界书使用 `ai_tavern_world_book_v1`，`spec_version` 为 `1.0`。建议按以下边界拆分条目：

- 长期不变的世界规则、组织、地理和能力体系分别成条目；
- 人物当前伤势、所在地点等短期状态不要写成永久世界规则；
- 只有始终需要进入上下文的核心规则才设 `constant=true`；
- 其余条目使用明确且不过宽的 `keys`；
- 因剧情确认而永久改变的事实，可以由运行时状态同步更新世界书。

完整包中的世界书必须是完整对象，不能只写文件名。

导入后，运行中的工作台会把世界书区分为四类来源：内置基础层、导入基础层、剧情动态层和玩家层。基础文件仍是作者交付物，不会因游戏内编辑被原位覆盖；玩家修改会保存为可撤销的修订覆盖层，并可查看逐字段差异或恢复基础版本。剧情临时状态仍不得写入世界书。

## 七、原文参考文件

推荐使用 UTF-8 Markdown，并以清晰标题分隔章节或场景：

```markdown
# 第一章 标题

正文……

# 第二章 标题

正文……
```

组装完整包时，将正文原样写入：

```json
{
  "name": "原文参考名称",
  "fileName": "原文参考_剧本名称.md",
  "content": "完整 UTF-8 正文",
  "currentChapter": 1,
  "preventFuture": true,
  "fidelity": "faithful",
  "enabled": true
}
```

`currentChapter` 表示普通原文引用允许检索到的进度，不是全文总章节数。开局通常设为 `1`，并启用 `preventFuture`，避免原作后续内容提前成为已经发生的事实。若同时使用 `faithful` 和剧情任务模块，程序可以从紧邻的下一章节提取少量防剧透导演锚点，用来约束角色提出的重大方案和关键机制；锚点不会自动成为角色知识，也不会在回合页面展开正文。

## 八、剧情任务模块

一个任务模块至少包含：

```json
{
  "id": "stable-module-id",
  "title": "任务标题",
  "objective": "对玩家不可见的当前推进目标",
  "completionCriteria": ["可以从实际剧情中判断的完成条件"],
  "activationConditions": ["启用前需要成立的剧情事实"],
  "prerequisiteModuleIds": ["前置任务 ID"],
  "continuityNotes": "允许哪些合理分支仍接续该任务",
  "autoContinue": true
}
```

编排任务链时遵守以下规则：

- `id` 在包内稳定且唯一，发布新版本时不要随意改名；
- 前置 ID 必须指向同一包内存在的任务；
- 前置关系不得形成循环；
- 可以让多个任务共享同一前置任务，作为可选分支；
- 启用条件必须来自已经发生的剧情事实，不能把未发生的原作事件当作事实；
- 完成条件必须能从对话、行动或状态变化中找到证据；
- `continuityNotes` 应允许玩家合理偏离，而不是要求系统强行回到原作；
- `opening.initialStoryModuleId` 必须指向已存在的任务，且与 `initialStoryDirection` 表达同一开局意图。

当前任务完成后，系统会结合前置关系、启用条件和剧情连续性选择可接续任务；若玩家已经明显脱离预埋路线，则沿当前事实生成新目标，并保留原任务历史。

## 九、开场内容

`opening.scene` 必须写成玩家进入游戏后直接阅读的正文，而不是给模型的提示词。它应包含：

- 明确的时间、地点和在场人物；
- 当前可感知的冲突或事件；
- 主要角色符合人物卡的言行；
- 一个自然交给玩家回应的落点。

不要在开场替玩家角色发言或决定行动，也不要把后续任务的结果提前写成已经发生。

## 十、版本号

| 文件 | 版本字段 | 当前建议值 |
| --- | --- | --- |
| 完整剧本包 | `spec_version` | `1.1`；仍兼容 `1.0` |
| 人物卡 | `spec_version` | `2.0` |
| 世界书 | `spec_version` | `1.0` |
| 完整运行存档 | `schemaVersion` | 由程序导出，当前为 `1.9.0` |
| 模型回合输出 | `schemaVersion` | `1.0.0` |

完整剧本包的 `bundle_version` 是作者维护的内容版本，例如 `2.1`，不等同于格式字段 `spec_version`。

## 十一、推荐的制作流程

1. 先建立维护目录和 `README.md`。
2. 分别完成人物卡、世界书和原文参考。
3. 在 `开局预设.json` 中编排开局表单与剧情任务链。
4. 运行 `bundle:check` 检查资料路径、任务图和内容格式。
5. 运行 `bundle:build` 自动内嵌全部内容并生成校验报告。
6. 实际导入一次，确认开场人物、地点、原文进度和当前任务正确。
7. 只发布通过验证的完整剧本包；如需方便二次创作，再附带拆分资料目录。

如果只有一份原文，可以先用首页分析人物与开场，确认分工后自动生成标准包；不满意时填写具体原因并只重做目标分区，再下载 JSON 审阅。需要长期维护或多次发布时，应把生成结果拆成上文目录结构，固定人物卡、世界书和任务 ID，并使用本地构建器重新校验；不要把每次重新调用模型当作稳定版本管理方式。

## 十二、发布前检查清单

- [ ] 完整包可以单文件独立导入。
- [ ] `spec_version` 与使用的字段版本匹配。
- [ ] 玩家、主要角色和其他角色分工正确。
- [ ] 所有其他角色都设置了 `presentAtOpening`。
- [ ] 世界书内容与人物卡没有互相矛盾。
- [ ] 原文 `content` 与源文件一致，`currentChapter` 没有越过开场进度。
- [ ] 任务 ID 唯一，前置 ID 有效且无循环。
- [ ] 初始任务 ID 存在，开局剧情走向与其目标一致。
- [ ] 开场是可直接阅读的剧情正文，不替玩家作决定。
- [ ] README、开局清单和完整包中的版本号一致。
